# In-App Documentation Page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `/docs` page in the SPA with two audience tabs (Business Users / Developers) documenting runtime usage and configuration of Ku-CRUD v1.5.

**Architecture:** One new static React page (`Docs.tsx`) under the authenticated `App` layout, toggled between two content sections via `useState`. Sidebar link + header title wired through the existing i18n dictionary; the documentation body itself is hardcoded English JSX.

**Tech Stack:** React 18, react-router-dom (HashRouter), Tailwind v3, existing shadcn primitives (`Button`, `Card`, `Badge`, `Separator`), lucide-react icons.

## Global Constraints

- English-only doc content, NOT routed through i18n dictionaries (spec decision).
- No new npm dependencies. No new UI primitives beyond existing shadcn components in `web/src/components/ui/`.
- Frontend only — no backend or metadata changes.
- `npm run build` (runs `tsc -b` strict) and `npm run lint` (oxlint) must pass.
- Follow existing code style: function components, `@/` path alias, `cn()` from `@/lib/utils` where needed.

- [ ] **Step 2: Write Business Users sections**

Sections (title → bullet content). Keep each bullet one to two sentences, user-facing wording, referencing UI elements by their English label:

1. **Getting started** — log in with the account your admin gave you; switch interface language (ID/EN) from the sidebar footer, preference is saved to your profile; your sidebar lists the tables you have access to.
2. **Working with the grid** — search box filters rows; click a column header to sort; pagination controls at the bottom (page size is set per table by the admin); **Group by** groups rows by a chosen column with per-group counts.
3. **Filtering data** — per-column advanced filters (operators depend on the column type: text contains/equals, number/date ranges, in-lists); active filters show as removable chips; **saved filters** — save the current combination under a name, reload it from the dropdown later; saved filters are private to you.
4. **Different views** — tables can be shown as **Grid**, **Kanban**, or **Calendar** (switch from the data page; the admin sets the default). Kanban: cards in columns per enum value; drag a card to another column to update that field (needs update permission; every drag is audited). Calendar: rows appear as events on the chosen date column; click an empty day to create a row with that date pre-filled; click an event to open the row.
5. **Adding and editing rows** — "New row" button and row menus (needs permission; buttons you can't use are hidden); relation fields open a searchable picker to choose a linked record; many-to-many fields are multi-select; JSON fields are shown formatted and validated before saving.
6. **Import & export** — **Export CSV** downloads what's on screen (current search/filter/sort applied, relation values included); **Import CSV**: upload a file (comma/semicolon/tab auto-detected, up to 5 MB / 10,000 rows), check the column mapping and per-row validation preview, then insert only valid rows or all rows; multi-select rows to **bulk delete** with one confirmation.
7. **Audit trail** — every create/update/delete (including imports, bulk deletes and kanban drags) is recorded with who/when/what; visible to users granted audit access.
8. **Messages you might see** — red **schema changed** banner: the table structure in the database no longer matches its definition; an admin must re-sync it; "row is referenced" error: the record is linked from another table and must be unlinked first; validation errors under a field: fix the value per the rule shown (e.g. email format, max length).

- [ ] **Step 3: Write Developer sections**

Sections:

1. **Datasources** — register Postgres/MySQL connections (driver, host, port, database, user, password, sslmode); **Test connection** before saving; passwords are stored encrypted (AES-256-GCM) in the metadata file; connections are opened on demand.
2. **Defining a table** — 3-step wizard: pick datasource → introspected table (columns/types/keys/enums read from `information_schema`, no DDL ever runs) → tune the definition: labels, editable/visible flags, search/sort flags, page size, default sort column+direction. Supported types: boolean, number, text, datetime, enum, uuid, json, fk, m2m (arrays/binary excluded).
3. **Keys** — key columns drive the update/delete WHERE predicate: single or composite; they don't have to be the real database PK, but at least one key column is required.
4. **Relations** — `fk` column points at another table definition (same or different datasource, self-reference allowed); choose the target and which fields display in grids/forms; forms pick records via searchable modal; edits happen on the referenced table's page. `m2m` virtual column models a junction table (a defined table with two fk columns — one to this table, one to the target); managing links needs create+delete grants on the junction; deleting rows that others reference is blocked with a conflict message.
5. **Validation rules** — per column, multiple rules per column: email format, min/max length, number-only, text-only; enforced server-side on create/update and in CSV import preview.
6. **Computed columns** — definition-level virtual columns with a formula from an allowlist (arithmetic `+ - * /` between number columns, concat between text columns, optional constants); evaluated server-side, never stored in the database; shown in grid/detail/CSV export but **cannot** be filtered, sorted, or searched server-side (the UI marks this).
7. **Formatting** — presentation only, values are stored untouched: enum badge colors per value, number thousands separator / decimal places / currency prefix, locale-aware datetime display.
8. **Views** — per table choose the default view (grid/kanban/calendar); kanban needs one enum column as the board column; calendar needs a datetime column (optional end-date column); drag-drop updates are subject to update grants and audited.
9. **Schema drift** — every page visit compares the live schema to the definition; on drift the UI shows a red banner listing missing/added/type-changed columns with one-click **Re-sync**.
10. **Moving definitions between instances** — export datasources + table definitions to one JSON file (passwords never included — re-enter them on import); import shows new/duplicate/conflicting definitions and lets you choose; relations are remapped.
11. **Users & roles** — first user is the immutable builtin Admin (CLI `seed-admin` is the recovery path); custom roles = Platform Management bundle (datasources, table definitions, audit) + independent read/create/update/delete grants per table; one role per user; disabled users are rejected at login; fk display values and the record picker only resolve for users with read access to the target table.
12. **Runtime security behavior** — login/setup rate limiting (5 failures / 15 min per username+IP → HTTP 429); 24h signed HttpOnly session cookie; all entity IDs in the API are opaque masked tokens; all SQL parameterized with identifier allowlisting; datasource passwords encrypted at rest.
