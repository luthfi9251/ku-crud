# V1.2 Phase 1 — Relational Table (Foreign Key) Design

Date: 2026-08-19
Status: Approved (brainstorming session)
Scope: V1.2 "Support for Relational Table" — Postgres only. Multi-adapter DB
(MySQL/MongoDB) is deferred to phase 2.

## Context

Ku-CRUD (Go + React) provides runtime-defined CRUD over user Postgres
databases. Today a column that references another table displays only the raw
reference value. V1.2 phase 1 adds user-defined foreign-key relations so the
grid and forms can show and pick related records.

Decisions from the brainstorming session:

1. **Delivery order**: FK relations on Postgres first; multi-adapter refactor
   comes after (phase 2).
2. **FK target** must be an existing Ku-CRUD table definition (its key
   columns are known, its page exists for redirects, RBAC applies).
3. **Relation semantics**: FK column on the source table (many-to-one; a
   unique FK column covers one-to-one). Reverse one-to-many display is out of
   scope for phase 1.
4. **Cross-datasource FK allowed** (per brief: "dimulai dari datasource,
   default datasource sama"). Display uses batched lookups, never JOIN, so
   same-DS and cross-DS behave identically.
5. **Delete protection**: block delete of a referenced row based on relations
   defined in Ku-CRUD metadata; surface DB FK violations as 409.
6. **Approach**: API-side batched enrichment (Option A). Backend enriches row
   responses with related data; frontend renders.

## Data model (SQLite metadata)

New nullable columns on the `columns` table:

| Column               | Contents                                                        |
|----------------------|-----------------------------------------------------------------|
| `base_type`          | mapped source-column type from introspection (`number`, `text`, …) used by drift detection |
| `fk_table_def_id`    | target table definition id                                      |
| `fk_ref_column`      | column of the target table used as the reference value           |
| `fk_display_columns` | JSON array of target column names shown in grid & form           |

`field_type` gains value **`fk`**. The UI presents FK as a column type (per
brief); the underlying introspected type is preserved in `base_type`.

Drift detection compares a def column's effective type (`base_type` when
`field_type='fk'`, else `field_type`) against the live column type, so FK
columns do not false-positive.

## Validation (table def create/update)

For `field_type='fk'`:

- `fk_table_def_id` must reference an existing table definition.
- `fk_ref_column` must be one of the target definition's columns.
- `fk_display_columns` must be a non-empty subset of the target definition's
  columns, unique names.
- `base_type` must be a valid field type.
- Self-reference (column pointing at its own table, e.g. `parent_id`) is
  allowed; relation expansion is one level deep, so no cycle handling.

## API behavior

### Row list & get — relation enrichment

`GET /api/tables/{id}/rows` (and row get) responses gain a top-level `rels`
object:

```json
{
  "rows": [{"id": 1, "customer_id": 5}],
  "total": 42, "page": 1, "pageSize": 20,
  "rels": {
    "customer_id": {
      "5": {"name": "ACME", "city": "Bandung"}
    }
  }
}
```

- Per FK column: collect unique non-null values from the page, run one
  `WHERE "ref_col" IN (...)` query against the target table selecting the ref
  column plus display columns; map `String(value) -> display fields`.
- If the requesting user lacks read permission on the target definition, that
  FK column is skipped in `rels` (the grid falls back to the raw value); the
  request still succeeds.
- Tables without FK columns pay zero overhead.

### New endpoint — modal picker

`GET /api/tables/{id}/fkoptions/{column}?search=&page=`

- `column` must be an FK column of definition `{id}`.
- Requires read permission on the source table AND the target table.
- Searches the target table's searchable columns, paginates using the target
  definition's page size, returns `{"rows": [...], "total": n, "page": p}`
  where rows carry the ref column and display columns.

### Create/Update with FK values

- A non-null value for an FK column must exist in the target table
  (`SELECT 1 ... WHERE ref_col = $1`); otherwise `400 VALIDATION
  "referenced row not found"`.
- Null remains valid subject to the existing required/nullable rules.

### Delete protection

- Before deleting, for every definition B with an FK column targeting this
  definition: count rows where `B.fkcol = old_row[fk_ref_column]`.
- Any count > 0 → `409 CONFLICT` with detail listing referencing tables and
  counts; the row is not deleted.
- Postgres `foreign_key_violation` errors from the live connection are
  mapped to the same 409 shape; other DB errors surface as today.

### Security

- Identifiers go through the existing `QuoteIdent` allowlist; ref/display
  columns are validated against stored target-def metadata before use; all
  values are parameterized.
- New query builder `BuildFetchByRefValues` follows the existing
  `BuildFetchByKey` pattern.
- Masked-id tokens are used for `fkTableDefId` in DTOs, consistent with other
  ids crossing the API boundary.

## Frontend

### TableForm wizard

- Column type selector gains "Foreign Key".
- Selecting it reveals: Datasource dropdown (default the source table's
  datasource) → Table dropdown (table defs in that datasource) → Ref column
  dropdown (target def columns) → Display columns multi-select.

### Grid (Data.tsx)

- FK cells render the related record's display fields from `rels`, joined
  with `" — "`. Falls back to the raw value when no entry exists
  (no permission or dangling reference).

### Create/Edit form

- FK field: read-only preview of the selected related record plus a "Pilih…"
  button opening the picker modal (search box, paginated list, click to
  select).
- The modal offers "Tambah baru" which navigates to the target table's page
  (`/data?table=<targetId>`) to create the record there, per brief.
- On edit, relation display fields are shown non-editable with an
  "Edit di table <target>" link redirecting to the referenced table's page —
  create/update/delete of related data always happens on the referenced
  table's own page (single source).

### Delete UX

- 409 responses render a message naming the referencing tables and counts.

## Testing

- **Unit (meta)**: migration of new columns; FK def validation rules; DTO
  round-trip including fk fields.
- **Unit (ds)**: `BuildFetchByRefValues` — identifier allowlist, placeholder
  numbering, empty value list.
- **Integration (KUCRUD_TEST_PG)**: parent/child schema plus a
  cross-datasource relation — CRUD flow, enrichment correctness (including
  null and dangling values), picker search/pagination/RBAC, invalid FK value
  rejected on create/update, delete blocked with 409, drift does not
  false-positive on FK columns.
- **Regression**: existing injection tests still pass; `go vet ./...`,
  `gofmt -l .`, and `npm run build` (strict type-check) clean.

## Out of scope (phase 1)

- Multi-adapter DB (MySQL, MongoDB) — phase 2 of V1.2.
- Reverse one-to-many child display.
- Sorting/searching on relation display fields.
- Inline editing of related records (single-source rule).
