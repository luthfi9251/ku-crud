# Ku-CRUD v1.5 — Multiple Views, Column Formatting, Computed Columns & Platform Polish (Design Spec)

Date: 2026-08-21
Status: Approved (decisions confirmed with owner)
Baseline: development @ 2859dd2 (v1.4 merged)

## 1. Goal

Shift the POV from "tool for people too lazy to open a SQL editor" to a **Low
Code CRUD for two personas**: a programmer who does the table-definition setup,
and a pure business user (no IT background) who consumes the tables. v1.5 makes
data present comfortably and readably for the business user:

1. Multiple views per table (Grid, Kanban, Calendar)
2. Column formatting (enum badges with colors, number format, locale-aware datetime)
3. Group-by on the grid
4. Computed (virtual, read-only) columns
5. Platform polish: UI localization (ID/EN per user) + per-user saved filters

Out of scope (per brief / owner): per-user view persistence, MongoDB, hooks
automation (v1.6), server-side grouping endpoints, group-by / filter / sort on
computed columns.

## 2. Owner decisions (confirmed)

| Question | Decision |
|---|---|
| Computed column evaluation | **Backend** — computed once in the row serializer, consistent across grid / detail / CSV export. |
| Formula model | **Mini expression string** — allowlisted grammar (`+ - * /` between number columns, `CONCAT(...)` between text columns, numeric/string literals). No free-form code. |
| Kanban data loading | **Lazy loading / infinite scroll per column** — each board column fetches its own pages reusing the v1.4 `filters` mechanism (`boardCol = value`). |
| Calendar scope | **Month view only** (prev/next/today), custom implementation, no new dependencies. |
| View persistence | **Session-only** for the user's switch; the *default* view is set globally on the table definition. |
| i18n scope | **All pages** — full extraction of every user-facing string into ID/EN dictionaries. |
| Saved filter contents | **Advanced filters only** (name + serialized filter JSON). Search term, sort and view mode are not saved. |
| Group-by data scope | **All matching rows** (search/filter/sort applied), pagination disabled, 2,000-row safety cap with a truncated notice. |
| Datetime display format | **Locale-aware, follows the user's language** (rendered client-side). |
| Architecture approach | **A** — views are frontend features on top of the existing `/rows` API; backend grows only computed columns, formatting config, `defaultView`/`view_config`, saved filters, and the per-user language. No new abstraction layers, no new dependencies. |

## 3. Feature designs

### 3.1 Computed Column (backend)

- `ColumnDef` gains `IsComputed bool` (`isComputed`) and `ComputedFormula string`
  (`computedFormula`). A computed column has no live schema counterpart:
  - introspection, drift compare and resync **skip** computed columns; resync
    preserves them.
  - `fieldType` is derived from the formula: `number` (arithmetic) or `text`
    (concat). `editable=false`, `sortable=false`, `searchable=false`; cannot be
    a filter column, group-by column, board column or calendar column.
- **Formula grammar** (strict allowlist, recursive-descent parser + evaluator,
  one small Go file):

  ```
  expr   := term (('+' | '-') term)*
  term   := factor (('*' | '/') factor)*
  factor := number | ident | '(' expr ')'
  concat := CONCAT '(' (ident | stringLiteral) (',' (ident | stringLiteral))* ')'
  ```

  - `ident` must resolve to a non-computed column name in the same definition;
    arithmetic operands must be `number` columns, `CONCAT` operands `text`
    columns (type-checked at definition save).
  - Numeric literals (decimal, optional minus) and double-quoted string
    literals allowed.
  - Evaluation in Go: arithmetic → `float64`, concat → string. **NULL in any
    operand → NULL result** (no error). **Division by zero → NULL**.
  - Computed columns reference only real columns — no chaining to other
    computed columns.
- **Evaluation point**: one shared helper applied in the row serializer used by
  `GET /rows` (list), `GET /rows/{key}` (single), and CSV export. Values are
  appended to the row as `row[colName] = <result>` (or `null`).
- **UI**: wizard gains "Add computed column"; a virtual column with name, label,
  type (number/text), and a formula input. Definition save runs parse +
  type-check; failure → 400 naming the column. Grid headers of computed columns
  show a small "fx" badge, are not sortable, and are excluded from the filter
  bar and group-by select (the UI must visibly mark that they cannot be
  filtered/sorted/search server-side).

### 3.2 Column Formatting (presentation only)

- `ColumnDef` gains `Formatting` JSON (`formatting`, same pattern as
  `validations`):

  ```json
  { "enumColors": { "paid": "green", "pending": "amber", "failed": "red" } }
  { "number": { "thousands": true, "decimals": 2, "prefix": "Rp " } }
  ```

  - `enum` columns: programmer optionally picks a color per enum value from a
    **limited palette** (gray, blue, green, amber, red, purple, cyan, orange).
    Unset values fall back to the current neutral badge.
  - `number` columns: thousands separator (toggle), decimals (0–6), optional
    currency/text prefix. Display only — the stored value never changes.
  - `datetime` columns: **always rendered locale-aware** following the user's
    language (no configuration knob).
  - Formatting for the wrong field type (e.g. `enumColors` on a number column)
    is ignored at render; `validateDef` rejects only structurally invalid values
    (unknown color, decimals out of range).
- **Applied surfaces**: grid, kanban cards, calendar events, edit/detail modal.
  **CSV export keeps raw values** (machine-readable).
- **UI wizard**: expanded column card — enum → per-value color picker; number →
  thousands toggle + decimals input + prefix input.

### 3.3 Multiple Views (frontend)

- `table_defs` gains `defaultView` (`grid|kanban|calendar`, default `grid`, set
  by the programmer) and `view_config` JSON:

  ```json
  { "kanbanBoardColumn": "status", "kanbanDisplayColumn": "title",
    "calendarStartColumn": "start_at", "calendarEndColumn": null }
  ```

- **View switcher** (segmented control in the Data page toolbar) shows only
  valid views: kanban when `kanbanBoardColumn` is set (must be a real enum
  column), calendar when `calendarStartColumn` is set (must be a real datetime
  column), grid always. The user's switch is session-local (resets to
  `defaultView` on each visit). If `defaultView` names a view that is not
  configured/valid for the table (e.g. `calendar` without a date column), it
  falls back to grid.

**Kanban** (frontend, on top of the existing `/rows` API):
- Board columns = the enum values of `kanbanBoardColumn`, plus a "No value"
  column for NULL rows.
- Each column lazy-loads its rows via **infinite scroll**: `GET /rows?filters=
  [active filters + boardCol = value]&page=N&limit=<pageSize>`, appending on
  scroll. Active search/filters apply per column.
- Card = `kanbanDisplayColumn` value + edit/delete actions (same grants as the
  grid). Actions open the existing row modal / delete mutation.
- **Drag & drop** between columns (native HTML5) → optimistic update + `PUT
  /rows/{key}` with `boardCol` = target enum value. Tied to the existing update
  grant and audit trail (endpoint unchanged); rollback on failure.

**Calendar** (frontend, month view only):
- Fetch `GET /rows?filters=[active filters + startCol between first..last day
  of the visible month]`; each row becomes an event at its start datetime.
- If `calendarEndColumn` is set, the event spans start→end (rendered clipped at
  the month boundary). Otherwise single-day.
- Click event → open the existing edit/detail modal; click a day → open the
  create modal with the clicked date pre-filled on the start column;
  prev/next/today navigation.

### 3.4 Group By on Grid (frontend)

- Group-by select in the grid toolbar (visible, non-computed columns only; raw
  column values — fk display and m2m are excluded).
- When active: fetch **all matching rows** (search + filters + sort applied) in
  page chunks up to a **2,000-row safety cap**; over the cap the UI shows
  "grouping truncated". Pagination is disabled while grouping.
- Rows are grouped client-side by the string form of the column value; each
  group header shows the value and the count within the fetched set. Group
  order follows the active sort. Row actions, bulk-select and CSV export keep
  working.
- Turning group-by off restores the paginated grid.

### 3.5 Saved Filters (per user)

- New metadata table `saved_filters` (migration 8). Owner-only visibility:
  `GET /api/tables/{id}/saved-filters` returns only the caller's own saved
  filters; `PUT`/`DELETE` on another user's filter → 404.
- Content = name (1–60 chars) + serialized v1.4 filter JSON (the exact shape of
  the `filters` query param). Validation at save: filters parse and each column/
  operator resolves against the current table definition → 400
  `FILTER_INVALID` otherwise.
- **UI**: "Save filter" button (enabled only when ≥1 filter is active) prompts
  for a name; a dropdown lists the user's saved filters for the current table
  with load / rename / delete. Loading sets the FilterBar state and resets the
  page to 1. Per-table; resets on table change.

### 3.6 Localization (ID/EN) + Language preference

- `users` gains `language` (`en|id`, default `en`). New endpoint
  `PATCH /api/auth/me` accepts `{language}` and updates the caller's profile.
- Frontend: a language context + `useT()` hook with dictionaries
  `web/src/lib/i18n/en.ts` and `id.ts`. **All user-facing strings across every
  page** are extracted (largest frontend surface of v1.5). Language selector in
  the sidebar footer. Datetime formatting is locale-aware (owner decision).
- No new dependencies — dictionary + hook implemented by hand (repo convention:
  no new npm packages).

## 4. Data model changes (migration 8)

```sql
ALTER TABLE columns ADD COLUMN formatting TEXT NOT NULL DEFAULT '';
ALTER TABLE columns ADD COLUMN is_computed INTEGER NOT NULL DEFAULT 0;
ALTER TABLE columns ADD COLUMN computed_formula TEXT NOT NULL DEFAULT '';

ALTER TABLE table_defs ADD COLUMN default_view TEXT NOT NULL DEFAULT 'grid';
ALTER TABLE table_defs ADD COLUMN view_config TEXT NOT NULL DEFAULT '';

ALTER TABLE users ADD COLUMN language TEXT NOT NULL DEFAULT 'en';

CREATE TABLE saved_filters (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id       INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  table_def_id  INTEGER NOT NULL REFERENCES table_defs(id) ON DELETE CASCADE,
  name          TEXT NOT NULL,
  filters       TEXT NOT NULL DEFAULT '',
  created_at    TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE UNIQUE INDEX idx_saved_filters ON saved_filters(user_id, table_def_id, name);
```

## 5. API surface summary (new)

| Method/Path | Gate | Purpose |
|---|---|---|
| `PATCH /api/auth/me` | auth | update own profile (language) |
| `GET /api/tables/{id}/saved-filters` | auth | list own saved filters |
| `POST /api/tables/{id}/saved-filters` | auth | create (`name`, `filters`) |
| `PUT /api/tables/{id}/saved-filters/{fid}` | auth (owner) | rename / replace |
| `DELETE /api/tables/{id}/saved-filters/{fid}` | auth (owner) | delete |

Changed: table-def payloads expose `defaultView`, `viewConfig`, and per-column
`isComputed`/`computedFormula`/`formatting`; row payloads (list / single /
export) include computed-column values. `filters` validation helper from v1.4
is reused for saved-filter validation. No changes to the `/rows` query surface —
kanban, calendar and group-by are pure frontend consumers of it.

## 6. Error handling

- `validateDef` additions (400 with the offending column/field named):
  - `defaultView` must be `grid|kanban|calendar`.
  - `view_config.kanbanBoardColumn` must exist, be a real (non-computed) enum
  column; `kanbanDisplayColumn` must exist and be visible (a computed column is
  allowed for the card title since row responses already include computed
  values); `calendarStartColumn`/`calendarEndColumn` must exist, be visible and
  be `datetime`.
  - Computed columns: formula must parse (parse error message), every `ident`
    must resolve to a non-computed column, operand types must match the chosen
    `fieldType`, chaining to computed columns rejected.
  - Formatting: colors from the palette, `decimals` 0–6.
- Saved filters: 400 `FILTER_INVALID` (unparseable / unresolvable filter),
  400 `VALIDATION` for name length; non-owner `PUT`/`DELETE` → 404 (existence
  is concealed to avoid leaking other users' filter names).
- Computed evaluation failures never fail a request: a column that cannot be
  evaluated yields `null` (documented behavior).

## 7. Testing

Backend (Go):
- Formula parser/evaluator unit matrix: precedence, parens, `CONCAT`, numeric
  and string literals, NULL propagation, division by zero → NULL, bad tokens,
  unknown ident, type mismatch (arithmetic over text), computed-reference
  rejection.
- Computed columns in list / single-row / CSV export (values present, NULL
  cases), resync preserves computed columns.
- Formatting + `defaultView` + `view_config` roundtrip and rejection cases
  (migration 8 schema test included).
- Saved-filters CRUD, uniqueness (per user+table+name), owner-only visibility
  and 404 on non-owner mutation, invalid filter payload rejected.
- `PATCH /api/auth/me` language persistence.

Frontend: `npm run build` (strict tsc) + `npm run lint` (oxlint) — repo
convention; no FE test framework.

  merged with `--no-ff` in dependency order:

## 9. Risks / trade-offs accepted

- View modes and group-by are client-side consumers of the existing paged API:
  kanban and calendar fetch multiple pages; group-by loops pages up to a 2,000
  row cap. Huge tables show truncated boards/groups — a documented ceiling with
  an obvious upgrade path (server-side grouping/aggregate endpoints later).
- Computed columns cannot be sorted/filtered/searched server-side; the UI
  marks them and the filter/group-by selects exclude them. Export includes them
  but formatting (thousands/currency/colors) is display-only — CSV stays raw.
- Native HTML5 drag & drop (no pointer-event library) matches the no-new-deps
  rule; touch support is limited to what the browser provides.
- Full i18n extraction is the largest frontend change; it is done after the
  feature work so feature UI is written against the `useT()` hook from the
  start where cheap.
- Datetime formatting and multi-day event clipping happen client-side with
  `Intl` — consistent across adapters since raw values travel to the browser.
