# Ku-CRUD v1.3 — Data Movement & Daily Productivity (Design Spec)

Date: 2026-08-20
Status: Approved (decisions confirmed with owner)
Baseline: v1.2 (main @ fea641e)

## 1. Goal

Make Ku-CRUD a daily working tool rather than a viewer: move data in/out (CSV),
act on many rows at once (bulk delete), model many-to-many relations, support
UUID/JSON columns, and close three known utility/security gaps (plaintext
datasource passwords, unthrottled login, no default sort).

Out of scope (per brief): MongoDB adapter, advanced per-column filtering (v1.4),
keyset pagination (v1.4), per-column validation rules (v1.4).

## 2. Owner decisions (confirmed)

| Question | Decision |
|---|---|
| Export scope | ALL matching rows: active search/sort applied, pagination ignored (not just current page). Hard cap 100,000 rows → error suggests narrowing search. |
| CSV delimiter (import) | Server auto-detects `,` `;` or tab from the first line. Export always uses comma. |
| M2M junction | Junction MUST be an existing table definition whose two fk columns are already defined (v1.2 pattern). Grants/keys/audit/drift of the junction reuse existing infra. |

Remaining decisions are delegated to this spec (owner asked for autonomy).

## 3. Feature designs

### 3.1 CSV Export

**Backend** — `GET /api/tables/{id}/rows/export` (RequireAuth, read grant).
Query params: `search`, `sort`, `dir` — identical parsing/validation to
`handleRowList` (sortable allowlist, LIKE escaping). No `page` param: all rows.

- Reuses `ListRows` + `CountRows`; abort with 400 `EXPORT_TOO_LARGE` when
  total > 100,000.
- Rows are written with `encoding/csv` (automatic quoting), UTF-8 BOM prefix so
  Excel renders Unicode correctly, `Content-Type: text/csv; charset=utf-8`,
  `Content-Disposition: attachment; filename="<tableName>-<yyyymmdd-HHMMSS>.csv"`.
- Header row = column **names** (not labels) so a round-trip import auto-maps.
- Columns included: `visible`, excluding `m2m` virtual columns' raw (m2m cells
  export their joined display values — see 3.4).
- Cell formatting mirrors the grid:
  - `fk` columns: resolved display values joined with `" — "` (only when the
    user has read grant on the target; otherwise raw value — same rule as grid).
  - `m2m` columns: joined display values `", "`.
  - `boolean` → `true`/`false`; null → empty; everything else `fmt.Sprint`
    of the scanned value.
- fk/m2m resolution reuses `buildRels` with chunked `IN` lists (chunks of 500
  source values) so exports of any size stay bounded.

**Frontend** — "Export CSV" button in the Data toolbar (next to Refresh).
Builds the same `search/sort/dir` params as the list query, `fetch`es as blob
(credentials included by same-origin default), reads filename from
`Content-Disposition`, triggers download via object URL.

### 3.2 CSV Import

Two stateless endpoints; the file is uploaded both times (≤5 MB), the server is
the single source of truth for parsing, mapping and validation. No server-side
session state.

**Preview** — `POST /api/tables/{id}/import/preview`
(`multipart/form-data`, field `file`). Requires **create** grant on the table.

1. Size limit 5 MB; parse with `encoding/csv`; delimiter sniffed from the
   first line (`,`, `;`, `\t` — the candidate that yields the most fields on
   line 1 wins; ties → comma). Max 10,000 data rows → 400 `IMPORT_TOO_LARGE`.
2. Auto-mapping: CSV header → column name, matched case-insensitively after
   trimming (also tries the column label as an alias). Unmapped headers and
   unmatched required columns are reported.
3. Per-row validation reuses the write path exactly: `editablePayload`-style
   required-on-insert check + `validateValue` per column type (uuid/json
  included), and `checkFKValues` batched by distinct values per fk column.
4. Response: `{delimiter, headers, mapping, unmapped, rows[], counts}`
   where each row = `{values, valid, errors: [{column, message}]}`.

**Apply** — `POST /api/tables/{id}/import/apply` (multipart: `file`,
`mapping` JSON part, `mode` = `valid` | `all`). Requires create grant.

- Server re-parses, applies the client mapping (mapping columns are validated
  against the definition — never trusted), re-validates.
- `mode=valid`: only validation-passing rows are inserted.
  `mode=all`: every row is attempted (app validation errors are ignored; DB
  errors still fail that row) — best-effort coercion per type.
- Rows are inserted one-by-one through the adapter in a single request (batch
  operation, partial success allowed); failures collected per row index.
- Every successful insert writes an audit `INSERT` entry (best-effort, same as
  the row create path). Response: `{inserted, failed, failures[]}`.

**Frontend** — dedicated page `#/data/:id/import` (3 stacked cards, following
the TableForm wizard pattern): upload + summary → mapping selects (per CSV
header: target column or "ignore") + preview table with per-row valid/invalid
badges and error reasons → actions: primary "Insert N valid rows", secondary
"Insert all M rows". Result card shows inserted/failed counts with per-row
errors, plus a back-to-grid link. `api.ts` gains FormData support (skip the
JSON Content-Type when body is FormData).

### 3.3 Bulk Delete

**Backend** — `POST /api/tables/{id}/rows/bulk-delete` JSON
`{keys: [encodedRowKey, ...]}`. Requires **delete** grant. Cap 1,000 keys per
request → 400.

Per key: decode row key → `referencedBy` conflict check (409-style per-row
failure, not request-level) → `DeleteByKey` → audit `DELETE` per deleted row.
Partial success allowed. Response: `{deleted, failed, failures: [{key, code,
message, detail}]}`.

**Frontend** — checkbox column in the Data grid (shadcn `checkbox` primitive,
vendored). Header checkbox = select all rows on the current page only.
Selection toolbar appears above the grid: "N selected" + Delete button →
native `confirm()` (consistent with existing patterns) → chunked requests
(500 keys each) → summary banner (X deleted, Y failed with reasons) → refresh.

### 3.4 Many-to-Many (junction table)

**Definition model** — new field type `m2m` as a **virtual column**: it has no
counterpart column in the live source table. New `ColumnDef` fields:

```
FieldType = "m2m"
M2MJunctionDefID  int64    json:"m2mJunctionDefId"    // defined table, != this def
M2MJunctionSrcCol string   json:"m2mJunctionSrcCol"   // junction fk column → THIS table
M2MJunctionTgtCol string   json:"m2mJunctionTgtCol"   // junction fk column → target table
M2MDisplayColumns []string json:"m2mDisplayColumns"   // display fields on target
```

- The virtual column `name` is auto-generated (`m2m_<junctionTable>_<tgtCol>`,
  sanitized, unique among the def's columns); `label` is user-editable.
- `validation (validateM2M)`: junction def exists and differs from this def;
  both junction columns exist and are typed `fk`; src column's fk target is
  this table; tgt column's fk target resolves to a defined table; src != tgt;
  display columns ⊆ target columns; ≥1 display column.
- Drift detection skips `m2m` columns entirely (nothing to compare against).
- Resync (`ReplaceColumns`) preserves existing `m2m` virtual columns: the
  rebuild from live introspection re-appends the def's m2m column rows.

**RBAC** — grid display of an m2m column requires read on junction + read on
target (else the cell renders em-dash, mirroring fk fallback). Editing links
(create/edit form save) requires create+delete grants on the **junction**
(managing links = inserting/deleting junction rows) in addition to the normal
create/update grant on the source table.

**Read path (grid + export)** — new adapter method
`FetchPairsByRef(schema, table, col string, vals []any, retCol string) (map[string][]any, error)`
(IN-list, chunked): for each page row's src ref value → list of target ref
values; then `FetchByRefValues` on the target for display columns. Returned in
the list/get response as `m2mRels: {colName: {srcVal: Row[]}}` (separate field
so the existing `rels` shape stays untouched). Self-referencing junctions
(both fk columns → this table) are allowed.

**Options picker** — `GET /api/tables/{id}/m2moptions/{column}`: resolves the
m2m config, then behaves like `handleFKOptions` against the target table
(search + pagination, sorted by target default sort). Requires read on source,
junction and target.

**Current links** — `GET /api/tables/{id}/rows/{key}/m2m/{column}` returns the
selected target ref values + display rows for the edit form.

**Write path** — after the source row insert/update commits:
- new row (create): insert junction rows `(srcRefVal, tgt)` for each selection;
  if the src ref column has no value in the payload, links are skipped with a
  warning surfaced in the response.
- edit: diff current links vs selection → insert added, delete removed
  (`DeleteByKey` on junction with its key columns = (src, tgt) is NOT assumed —
  delete uses the junction's own configured key columns where possible;
  implemented as scoped delete `WHERE src=? AND tgt=?` via a new adapter
  builder `buildDeletePairs`).
- every junction insert/delete writes an audit row against the junction def.

**Delete protection** — deleting a row that has m2m links is **blocked** with
the standard conflict message. This falls out automatically: the junction's fk
columns target this table, so the existing `referencedBy` check (v1.2) already
counts them. No cascade deletes anywhere.

**Wizard UI** — in `ColumnListEditor`, a separate "Many-to-many relations"
section (below the live columns): add/relation cards with junction table
select (defined tables only), source fk column select (junction fk columns
whose target is this table), target fk column select (remaining fk columns),
display-columns toggle grid (target's columns). Stored in the same `columns`
payload as field type `m2m`.

**Form UI** — `M2MField`: chips of selected display values + "Pilih…" button
opening a multi-select variant of the existing FkField picker dialog (search,
pagination, add-new cross-navigation preserved). Removed chips unselect.

**Grid cell** — display values joined `", "`, truncated, tooltip with full list.

### 3.5 UUID & JSON column types

- `validFieldTypes` += `uuid`, `json` (backend) and `FieldType` union (TS).
- Postgres `MapFieldType`: `uuid` → `uuid`; `json`, `jsonb` → `json`.
- MySQL `mapMySQLType`: `json` → `json`. UUID has no native MySQL type — not
  auto-mapped, but a text-family column can be manually retyped `uuid` in the
  wizard (drift will then report it as a type change; acceptable and documented,
  same as any manual type override).
- `validateValue`: `uuid` — strict 36-char canonical form
  (`^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$`,
  nil UUID included); `json` — `json.Valid`. Both run before any insert/update
  and on every CSV import row.
- Drift `EffectiveType` compares `uuid`/`json` as first-class types.
- Frontend:
  - form: `uuid` → mono text input; `json` → vendored `textarea` showing
    `JSON.parse → stringify(…, 2)` on load; submit blocked client-side when
    the text does not parse (server still validates).
  - grid: `json` cells render pretty-printed, `line-clamp`ed (≈3 lines),
    mono, `whitespace-pre-wrap`; uuid renders mono text.
  - searchable/sortable flags work as text (existing `::text` / `CAST` casts
    in search SQL already cover both types).

### 3.6 Quick wins

**Datasource password encryption** — AES-256-GCM; 32-byte random key generated
once and stored in the `settings` table (`dsn_crypt_key`), same lifecycle as
the session/ID secrets. Stored ciphertext = `v1:` + base64(nonce‖ct).
Encrypt/decrypt lives entirely inside `internal/meta` datasource
create/update/get/list; `ds.Open` keeps receiving plaintext. A post-migration
Go pass encrypts any legacy plaintext row (idempotent: skip `v1:`-prefixed).
README security note updated honestly: this removes plaintext from casual
reads/dumps of the DB file; the key lives in the same file, so it is hardening,
not a security boundary.

**Login rate limit** — in-memory sliding window in front of `handleLogin`:
key = lowercase(username) + client IP (host of RemoteAddr); ≥5 failed attempts
within 15 minutes → 429 `RATE_LIMITED` with retry-after hint until the window
clears; successful login resets the counter. Per-instance state only (single
binary deployment model). Applies to `POST /api/setup` too (same protection).

**Default sort** — new `TableDef` fields `defaultSortCol` (default `""`) and
`defaultSortDir` (`ASC`|`DESC`, default `ASC`), set in the wizard's step-3
header next to label/page size (column select limited to sortable columns).
Server fallback order in `handleRowList`/export/fkoptions when no explicit
sort: explicit sort → default sort (if set and still sortable & existing) →
`keyColumns[0] ASC`. The Data page initializes its sort state from the def.
Legacy defs: empty default = current behavior, no migration backfill needed.

## 4. Data model changes (migration 6)

```sql
ALTER TABLE table_defs ADD COLUMN default_sort_col TEXT NOT NULL DEFAULT '';
ALTER TABLE table_defs ADD COLUMN default_sort_dir TEXT NOT NULL DEFAULT 'ASC';
ALTER TABLE columns ADD COLUMN m2m_junction_def_id INTEGER NOT NULL DEFAULT 0;
ALTER TABLE columns ADD COLUMN m2m_junction_src_col TEXT NOT NULL DEFAULT '';
ALTER TABLE columns ADD COLUMN m2m_junction_tgt_col TEXT NOT NULL DEFAULT '';
ALTER TABLE columns ADD COLUMN m2m_display_cols TEXT NOT NULL DEFAULT '';
```

Plus the Go-side lazy password-encryption pass (not expressible as pure SQL).
`dsEncKey` generated on demand. Old binaries reading a v6 DB would see
ciphertext passwords — acceptable (documented upgrade note: v1.3+ only).

## 5. API surface summary (new)

| Method/Path | Gate | Purpose |
|---|---|---|
| `GET /api/tables/{id}/rows/export` | auth + read | CSV download (search/sort applied, all rows) |
| `POST /api/tables/{id}/import/preview` | auth + create | parse/map/validate, no writes |
| `POST /api/tables/{id}/import/apply` | auth + create | batch insert + audit |
| `POST /api/tables/{id}/rows/bulk-delete` | auth + delete | per-row delete + audit |
| `GET /api/tables/{id}/m2moptions/{column}` | auth + read×3 | multi-select picker options |
| `GET /api/tables/{id}/rows/{key}/m2m/{column}` | auth + read×3 | current links for edit form |

List/get row responses gain `m2mRels`. Table def payloads gain
`defaultSortCol/defaultSortDir` and m2m column fields.

## 6. Error handling

- All new endpoints use the existing `writeErr` envelope `{code, message, detail}`.
- Import/bulk-delete are partial-success by design: per-row failures carry
  row index + reason; request-level failures (grants, drift, size caps,
  malformed multipart/mapping) reject the whole request.
- Export/import cap violations: 400 `EXPORT_TOO_LARGE` / `IMPORT_TOO_LARGE`
  with actionable messages.
- Rate-limited login: 429 `RATE_LIMITED`.
- m2m save with missing junction grants: 403 with a message naming the
  junction table; links left untouched, parent row write still rejected as a
  whole (single request, no partial parent/link state).

  behavior; AES-GCM password roundtrip + legacy-plaintext migration; default
  sort fallback resolution; `validateValue` uuid/json; drift skipping m2m;

  create-grant 403), bulk delete (success/conflict/audit/cap), m2m end-to-end

  protection), uuid/json column roundtrips + invalid-value 400s, default sort.

Frontend: `npm run build` (strict tsc) + `oxlint` must pass (repo has no FE
test framework; none introduced).

plus the `KUCRUD_TEST_PG`/`KUCRUD_TEST_MYSQL` variants via docker compose.

## 9. Risks / trade-offs accepted

- Import apply is not transactional (partial success) — matches the brief's
  "insert valid only or all" semantics; per-row reporting covers reconciliation.
- Password encryption key co-located with ciphertext (settings table) —
  documented as hardening, owner accepted the quick-win framing.
- m2m link deletion uses scoped `WHERE src=? AND tgt=?` regardless of the
  junction's declared key columns — deterministic for 2-FK junctions and immune
  to odd junction key configs.
- Export loads all rows into memory up to the 100k cap — bounded, acceptable
  for a metadata-driven tool.
- No FE test framework introduced (repo convention); FE correctness gated by
  strict TS build + lint + manual verification in dev mode.
