# Ku-CRUD v1.1 — Security & Utilities Design Spec

Date: 2026-08-19
Source: `project-brief.txt` (Fitur v1.1) + clarifications from project owner (recorded below).
Scope: all four v1.1 features. Core v1 functionality is preserved.

## Owner decisions (from clarification round)

1. **Platform Management** = one bundle switch (not per-module).
2. **Table CRUD permissions** = 4 independent switches per (role, table): read / create / update / delete. Free combination allowed.
3. **Tables without PK** = wizard requires at least 1 key column (composite allowed, does not have to be the real Postgres PK). No keyless definitions.
4. **ID masking scope** = ALL SQLite entities exposed via API/URLs: datasources, table defs, users, roles, audit entries.
5. **Upgrade from v1.0** = every existing user is assigned the Admin role.

## Interpretation notes (owner unavailable, resolved by analysis)

- Brief says only Admin may manage ROLE and USER ("Admin yang berhak mengatur ROLE dan USER"), while listing User Management under the Platform Management menu family. Resolution: **User Management and Role Management endpoints are Admin-only (`is_admin`)**. The platform_manage bundle gates Datasources, Tables & Schema, and Audit Trail. A non-admin platform manager does not get user management (managing users is explicitly admin-only per brief; a read-only user list for non-admins would leak user enumeration for no benefit).
- Admin role is builtin (`is_admin=1`), immutable via API, and implicitly holds ALL permissions: full platform access and full CRUD (read/create/update/delete) on every table definition, present and future — no grant rows are stored for Admin.
- "First User tidak dapat diubah ataupun didelete" is implemented literally: the first user (`is_first=1`) cannot be modified or deleted through the API at all (no rename, no password change, no role change, no disable). Recovery remains `cmd/seed-admin` (CLI, not API).
- Brief asks non-200 responses to be logged as errors. Implementation logs 5xx at ERROR and 4xx at WARN (both include the app error code/message); logging every unauthenticated 401 probe at ERROR would be noise. This satisfies the intent (no silent failures).

## 1. Multi-user management with roles

### Data model (SQLite migration 3)

```sql
CREATE TABLE roles(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE,
  is_admin INTEGER NOT NULL DEFAULT 0,
  platform_manage INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP);
CREATE TABLE role_table_grants(
  role_id INTEGER NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  table_def_id INTEGER NOT NULL REFERENCES table_defs(id) ON DELETE CASCADE,
  can_read INTEGER NOT NULL DEFAULT 0,
  can_create INTEGER NOT NULL DEFAULT 0,
  can_update INTEGER NOT NULL DEFAULT 0,
  can_delete INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY(role_id, table_def_id));
ALTER TABLE users ADD COLUMN role_id INTEGER NOT NULL DEFAULT 1;
ALTER TABLE users ADD COLUMN disabled INTEGER NOT NULL DEFAULT 0;
ALTER TABLE users ADD COLUMN is_first INTEGER NOT NULL DEFAULT 0;
UPDATE users SET is_first=1 WHERE id=(SELECT MIN(id) FROM users);
INSERT INTO roles(id,name,is_admin,platform_manage) VALUES(1,'Admin',1,1);
```

All existing users get `role_id=1` (Admin). No FK on `users.role_id` (SQLite ADD COLUMN cannot add REFERENCES with a non-NULL default); integrity is managed by the application (roles cannot be deleted while in use).

- First user creation (`/api/setup` and `seed-admin`) assigns the Admin role and `is_first=1` when it is the first user.
- Login rejects disabled users (generic 401, same as bad credentials). An existing session of a disabled user is rejected at `RequireAuth` (per-request user lookup sees `disabled=1` → 401).
- Deleting a table def cascades its grant rows. Deleting a role is refused while any user holds it.

### Permission model

- `CtxUser` gains `RoleID`, `IsAdmin`, `PlatformManage`, fetched per request by a single JOIN (`users` × `roles`), along with the disabled check.
- Middleware helpers following the existing `RequireAuth` pattern: `RequirePlatform` (403 `FORBIDDEN` unless PlatformManage/Admin) and `RequireAdmin` (403 unless IsAdmin).

Route → gate matrix:

| Route | Gate |
|---|---|
| health, login, logout, setup/*, auth/me | public / authed |
| `GET/POST /api/datasources`, `PUT/DELETE /api/datasources/{id}`, `/test`, `/tables`, `/tables/{s}/{t}/columns` | Platform |
| `GET /api/tables` | Authed — returns ALL defs for platform users, only defs with `can_read` for others |
| `POST /api/tables`, `PUT/DELETE /api/tables/{id}`, `/verify`, `/resync` | Platform |
| `GET /api/tables/{id}` | Authed + (Platform OR `can_read`); response includes `permissions` for the caller |
| `GET/POST /api/tables/{id}/rows` | `can_read` / `can_create` |
| `GET/PUT/DELETE /api/tables/{id}/rows/{key}` | `can_read` / `can_update` / `can_delete` |
| `GET /api/audit` | Platform |
| `GET/POST /api/users`, `PUT/DELETE /api/users/{id}` | Admin |
| `GET/POST /api/roles`, `PUT/DELETE /api/roles/{id}` | Admin |

Platform manage does NOT imply any table CRUD rights (the brief defines them as separate features); only Admin has implicit full table access.

### New endpoints

- `GET /api/users` → users with role name, disabled, isFirst.
- `POST /api/users` `{username, password, roleId}` — username unique/non-empty/≤64, password ≥ 4 chars.
- `PUT /api/users/{id}` `{password?, roleId?, disabled?}` — 403 for first user; 400 for self-disable/self-delete; username immutable.
- `DELETE /api/users/{id}` — 403 for first user, 400 for self.
- `GET /api/roles` → roles with grants and user counts.
- `POST /api/roles` `{name, platformManage, tables:[{tableDefId, canRead, canCreate, canUpdate, canDelete}]}`.
- `PUT /api/roles/{id}` — replaces grants atomically. Builtin Admin role (is_admin) is immutable (403).
- `DELETE /api/roles/{id}` — refused (400) while assigned to any user; Admin builtin refused.
- `GET /api/auth/me` → `{username, isAdmin, platformManage}`.

## 2. Composite key support

- `table_defs`: drop `pk_column`, add `key_columns TEXT NOT NULL` holding a JSON array. Migration copies `pk_column` → `json_array(pk_column)`. (DROP COLUMN requires SQLite ≥ 3.35 — modernc.org/sqlite current is far newer; verified by migration test.)
- `TableDef.KeyColumns []string` (`keyColumns` in JSON). `validateDef`: ≥1 key column, no duplicates, each must pass `QuoteIdent` and exist among the defined columns.
- `ds` builders become key-based: `BuildUpdateByKey`, `BuildDeleteByKey`, `BuildFetchByKey` take `keyCols []string, keyVals []any` and emit `WHERE "a"=$n AND "b"=$m`.
- Row key transport in `rows/{key}`: always a base64url(RawURLEncoding) of a JSON array of the key values as strings, e.g. `["3"]` → `WyIzIl0`, `["1","a"]` → `WyIxIiwiYSJd`. Backend decodes, checks length == len(keyColumns), rejects null members, coerces each value by its column field type (existing `coercePK`).
- Resync refuses if any key column disappeared from the live schema (was: PK dropped).
- Sort fallback (non-sortable column) uses the first key column.
- Audit `row_pk` stores the JSON array string (e.g. `["1","a"]`) for new entries; frontend parses with fallback to the legacy plain string.
- Wizard step 3: key selection changes from radio (single PK) to checkboxes (≥1 required, prefilled with all introspected PK columns). Data grid edit/delete use the encoded composite key; rows with a null key value get no edit/delete buttons.

## 3. Security hardening

### 3.1 SQL injection review (existing + new)

Existing defenses stay: `QuoteIdent` allowlist `^[A-Za-z_][A-Za-z0-9_]*$` on every identifier, sort column checked against defined sortable columns + direction forced to ASC/DESC, search restricted to defined searchable columns, fully parameterized values, unknown body keys rejected, value typing per field type.

Additions/verifications for v1.1:

- Key columns, role names, usernames validated for length/content (non-empty, ≤64; identifiers additionally via QuoteIdent).
- Audit filter values stay parameterized.
- LIKE wildcards in the search term (`%`, `_`, `\`) are escaped and `ESCAPE '\'` is appended, so search input can no longer alter matching semantics (defense-in-depth; values were already parameterized).
- Regression tests: API-level injection attempts against sort/dir/search/key columns payload (expect 400 or inert behavior), ds-level golden SQL tests for the composite builders.

### 3.2 ID masking — `internal/tokenid`

- 64-bit Feistel permutation (4 rounds, HMAC-SHA256 round function keyed by a dedicated `id_secret` setting — 32 random bytes hex stored in `settings`, generated once like the session secret). Domain separation per entity kind (`ds`, `td`, `user`, `role`, `audit`) is mixed into the round function input.
- `Encode(kind string, id int64) string` → deterministic, 11-char base64url token. `Decode(kind, token) (int64, error)`. Decode of a foreign/invalid token yields a parse error or a wrong-but-valid id that then 404s at lookup — tokens are unforgeable (HMAC) and not decodable into a chosen id.
- Applied on the way out: every `id`/`datasourceId`/`tableDefId`/`userId`/`roleId` in API responses is a masked token string (frontend types change `id: number` → `id: string`).
- Applied on the way in: every `{id}` path segment, the audit query filters (`tableDefId`, `userId`), and payload fields (`datasourceId` on table defs, `roleId` on users, `tableDefId` in role grants) are decoded via the codec.
- Live row values (`rows/{key}`) are NOT masked (they are user data, not SQLite ids).

## 4. Logging

- `log/slog` with a JSON handler on stdout, set up in `cmd/main.go`.
- Request middleware wraps the whole mux in `Routes()`:
  - access line for every request: method, path, status, duration ms; level INFO (2xx/3xx), WARN (4xx), ERROR (5xx).
  - non-2xx responses additionally carry the app error `code` and `message`: `writeErr` stashes them into a per-request context value the middleware reads back. No double logging.
- Startup, migration, audit-failure logs go through slog. Existing behavior (audit write failure never blocks a CRUD action) is preserved.

## Frontend (React) changes

- `lib/types.ts`: ids become strings; `TableDef.keyColumns: string[]`; new `User`, `Role`, `TableGrant`, `Me` types.
- `auth/me` drives the sidebar: Datasources (platform), Tables & Schema (all users — the page doubles as the table list home), Audit Trail (platform), Users & Roles (admin); per-table quick links only for tables the API returns (already grant-filtered). Version badge → v1.1.
- New pages `Users.tsx`, `Roles.tsx` (roles editor includes the per-table 4-switch grant matrix); routes `/users`, `/roles`.
- `TableForm.tsx`: multi-key checkboxes, `keyColumns` payload.
- `Data.tsx`: composite key encode helper; create/edit/delete buttons gated by the `permissions` object returned with the table def; drift banner unchanged.
- `Tables.tsx`: platform-only create/edit/delete controls.
- `Audit.tsx`: token ids, JSON-array row key display with legacy fallback, username shown from API.
- `Datasources.tsx`: id type only.

## Testing strategy

TDD per layer, following repo conventions (plain `testing`, white-box, table-driven where natural):

1. `internal/tokenid`: roundtrip, determinism, 11-char base64url charset, invalid input errors, domain separation, distinctness over id range.
2. `internal/meta`: migration-3 upgrade from a simulated v1.0 DB (roles seeded, users → Admin, is_first set, key_columns copied), users CRUD/login/disable, roles CRUD + grants replace + in-use guard, keyColumns persistence, id_secret generation.
3. `internal/ds`: golden SQL for composite update/delete/fetch, search LIKE-escaping goldens.
4. `internal/api`: RBAC 403 matrix, admin bypass, users/roles endpoint validation (first-user immutability, self-protection), masked-id roundtrip on every `{id}` route, composite-key row CRUD + audit against live PG, logging middleware output assertions (buffered slog handler).
5. Frontend: `tsc -b` strict typecheck + `vite build` (repo gate), `oxlint`.

## Out of scope

Cookie `Secure` flag, rate limiting, password hashing cost changes, datasource password encryption at rest, renaming users.
