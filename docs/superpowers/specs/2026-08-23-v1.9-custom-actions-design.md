# Ku-CRUD v1.9 — Customizable Table Actions (Design Spec)

Date: 2026-08-23
Status: Approved (design sections confirmed with owner)
Baseline: development @ 27ce570 (v1.8 query views merged)

## 1. Goal

Let the programmer control what the data grid can do, per table definition:

1. **Show/hide built-in actions** — each of the 7 built-in grid actions
   (new row, edit, delete/bulk-delete, copy, import, export, refresh)
   can be hidden per table. Presentation only; RBAC remains the only
   security boundary.
2. **Custom row actions powered by Go hooks** — programmer-defined buttons
   in each row's Actions cell that run an assigned hook synchronously,
   show the hook's result message as a toast, and refresh the grid.
   Executions are audited.

Approach (owner decision): **table-definition-centric** — both parts are
stored on the table definition and edited in a new "Actions" section of
the definition wizard. Hook logic stays global/reusable; only assignment
metadata (label, grant, confirm, order) is per-table.

Out of scope: toolbar-level (bulk) custom actions, custom actions in
kanban/calendar views, async (outbox) actions, per-column actions,
icon picker for custom buttons.

## 2. Owner decisions (confirmed)

| Question | Decision |
|---|---|
| Meaning of "customize actions" | Both: hide built-ins AND add hook-powered custom actions. |
| Custom action execution | **Synchronous** inside the request; hook result message shown as toast; grid refreshes. Optional confirm dialog per action (GroceryCRUD-callback feel). |
| Custom action placement | **Row-level only** — buttons in the grid Actions column. |
| Hideable built-ins | All 7: new row, edit, delete (incl. bulk-select column), copy, import, export, refresh. |
| Custom action permission | **Grant chosen per action** (`read` / `create` / `update` / `delete` on that table). Button shows only for users holding the grant; the endpoint enforces it too. |
| Audit | Every custom action execution writes an audit entry (user, action, row key, outcome). |
| View scope | **Grid view only.** Kanban/calendar unchanged. |
| Query-backed definitions | Custom actions unavailable (`QUERY_READONLY`); hide-list still applies to the grid toolbar (export/refresh). |
| Hidden vs RBAC | Visible = has grant AND not hidden. Hide always wins; hiding is never a security control. |

## 3. Data model

Migration 11 adds one column, following the `hooks` precedent:

```sql
ALTER TABLE table_defs ADD COLUMN actions TEXT NOT NULL DEFAULT '';
```

`TableDef.Actions string` (json `-`, like `Hooks`), parsed/validated by
`internal/hooks` (new `ParseActions`) into:

```go
type ActionsConfig struct {
    Hidden []string      // keys: newRow,edit,delete,copy,import,export,refresh
    Custom []CustomAction
}

type CustomAction struct {
    ID      string          `json:"id"`      // unique within the definition
    Label   string          `json:"label"`   // required, non-empty
    Confirm string          `json:"confirm,omitempty"` // optional confirm text
    Grant   string          `json:"grant"`   // read|create|update|delete
    Hook    string          `json:"hook"`    // registered hook name
    Config  json.RawMessage `json:"config,omitempty"`
    Order   int             `json:"order"`
    Style   string          `json:"style"`   // neutral|primary|danger (default neutral)
}
```

Validation (definition save + import):
- valid JSON; `hidden` keys from the fixed set; `custom` entries have
  non-empty unique `id`, non-empty `label`/`hook`, `grant` from the 4
  values, `style` from the 3 values, `config` (when present) any valid JSON.
- custom `id` is a slug (`^[a-zA-Z0-9_-]{1,64}$`) — it travels in the
  request body, so it is bounded and cannot be confused with a hook name.

The actions JSON is part of `TableDef`, included in metadata export/import
verbatim (same policy as `hooks`).

## 4. Hook contract changes (internal/hooks)

- New event constant `OnAction Event = "onAction"`. It is NOT part of the
  `Assignments` CRUD map (`ParseAssignments` still rejects it there);
  it exists so `HookFunc` implementations can branch on it and so the
  audit/outbox layers share one Event vocabulary.
- `RowPayload` gains `Message string` — set by `onAction` hooks, ignored
  by before/after hooks (additive, backward compatible).
- New executor entry: `RunAction(ctx, hc, row, a Assignment) (string, error)`
  — resolves the hook (missing → `MissingError`), runs it under
  `runGuarded` with new `ActionTimeout = 15 * time.Second`, returns the
  hook's `Message`.
- Modified values returned by an `onAction` hook are NOT written back —
  custom actions are side-effect + message only. The hook itself has full
  platform access (adapters, store, logger) if it wants to persist changes.
- New `ParseActions(s string) (ActionsConfig, error)` + hide-key/grant/style
  validation lives beside `ParseAssignments`.

## 5. API

One new endpoint:

```
POST /api/tables/{id}/rows/{pk}/action    body: {"actionId": "act_1"}
```

Handler flow (internal/api/actions.go):
1. Resolve table definition (404), reject query-backed defs with 403
   `QUERY_READONLY` (consistent with every other write path).
2. Parse actions config, find custom action by id (404 `ACTION_NOT_FOUND`).
3. Check the acting user's per-table grant for `action.Grant` (403).
4. Load row via adapter by encoded key (404 when missing) — the row is the
   source of truth for hook input, not the client.
5. Check hook registered (400 `HOOK_MISSING` — drift is never silent).
6. Execute via `RunAction` (timeout + panic recovery). Any hook failure —
   returned error, panic, or timeout — is a 400 `ACTION_FAILED` carrying
   the hook's error message.
7. Audit best-effort on BOTH outcomes (owner decision): `action="ACTION"`,
   RowPK = row key, NewValues = `{actionId, label, message, status}`
   (status `ok` with the hook message / `error` with the failure text).
8. Respond `200 {"message": "<hook message>"}`.

Table definition GET/PUT carry `actions` as a raw JSON string field
(same pattern as `hooks`); PUT validates via `ParseActions`.

## 6. Frontend

**TableForm (step 3)** — new "Actions" card beside Hooks/Views:
- 7 switches for built-in action visibility (default all ON).
- Custom action list editor: add/remove/reorder (up/down buttons, same
  pattern as HooksEditor ordering); per action: label, hook dropdown
  (from `GET /api/hooks`), grant select (read/create/update/delete),
  optional confirm text, style select (neutral/primary/danger), optional
  config JSON textarea (validated before save).

**Data.tsx (grid only)**:
- Toolbar: hidden built-ins are not rendered (all still AND-ed with perms
  and, for import/new-row, with `perms.create` as today).
- Bulk-select checkbox column disappears when `delete` is hidden (it only
  feeds bulk delete).
- Row Actions cell: custom buttons render before the built-in icons,
  ordered by `order`; icon button + tooltip = label; color follows style
  (danger → destructive red, primary → blue, neutral → muted).
- Click flow: `confirm(text)` when confirm text set → POST → toast the
  returned message (or error toast) → `rows.refetch()`.
- KanbanView/CalendarView untouched.

**i18n**: every new key in BOTH `web/src/lib/i18n/en.ts` and `id.ts`.
