# Ku-CRUD v1.7 — Business UI Polish (Design Spec)

Date: 2026-08-22
Status: Approved (approach A confirmed with owner)
Baseline: development @ b875186 (v1.6 merged)

## 1. Goal

Make the UI presentable for pure business users (no IT experience) while
keeping one application — the view adapts to the role. Two concrete pain
points drive this version:

1. Business users today are granted *Platform Management* just to get part
   of it, so they see every technical admin menu (datasources, definitions,
   users, audit, outbox).
2. Table menus and the data page read "developer": raw-ish labels, no
   description, and technical error messages (`HOOK_REJECTED`, drift
   banners, SQL-ish validation text) are shown as-is.

Deliverables:

1. Split the monolithic `platform_manage` boolean into four independent
   grants: `manageDatasources`, `manageTables`, `viewAudit`, `viewOutbox`.
2. Table definition gains an optional `description`; the label field is
   made prominent in the wizard with a live menu preview; description
   surfaces in the sidebar (tooltip) and under the data page title.
3. Humanized error messages in the frontend: error codes map to friendly
   ID/EN sentences via i18n; technical detail stays available but collapsed.

Out of scope: business homepage / dashboard, global search, pinned
favorites, table drag-reordering, a separate business shell or per-user
"simplified mode" toggle, backend message changes (mapping is
frontend-only), new API surface for third parties.

## 2. Owner decisions (confirmed)

| Question | Decision |
|---|---|
| Separate views vs one app | **One app, role-driven shell** — what you can do is what you see. No second SPA, no per-user mode toggle. |
| Grant granularity | **Four grants** as listed above. User & role management stays Admin-only (`RequireAdmin`, unchanged). Admin implicitly has all four. |
| Old `platform_manage` column | **Dropped in migration 10** after backfill — one-way, no compat shim. The API field `platformManage` disappears in the same release (frontend ships together with backend). |
| Table list visibility rule | The old "PM sees all tables" rule becomes **`manageTables` sees all table definitions** (they define them). Datasource/audit/outbox grants alone do not unlock data visibility — per-table read grants still govern. |
| Meta export/import gate | Requires **both** `manageDatasources` and `manageTables` (the transfer touches both kinds of entities). |
| Description storage | Column on `table_defs`, included in metadata export/import like other definition attributes. |
| Error humanization | **Frontend-only** mapping keyed by API error code; unknown codes fall back to the raw message. Technical detail behind a "view technical detail" disclosure. |

## 3. Grant model

### 3.1 Database (migration 10)

```sql
ALTER TABLE roles ADD COLUMN manage_datasources INTEGER NOT NULL DEFAULT 0;
ALTER TABLE roles ADD COLUMN manage_tables      INTEGER NOT NULL DEFAULT 0;
ALTER TABLE roles ADD COLUMN view_audit         INTEGER NOT NULL DEFAULT 0;
ALTER TABLE roles ADD COLUMN view_outbox        INTEGER NOT NULL DEFAULT 0;
UPDATE roles SET manage_datasources = platform_manage,
                 manage_tables      = platform_manage,
                 view_audit         = platform_manage,
                 view_outbox        = platform_manage;
ALTER TABLE roles DROP COLUMN platform_manage;
```

Plus (same migration): `ALTER TABLE table_defs ADD COLUMN description
TEXT NOT NULL DEFAULT '';`

Fresh databases run all migrations in order; the builtin Admin role
(is_admin=1) bypasses all gates via `IsAdmin`, so the backfill only
matters for upgraded custom roles.

### 3.2 Go types

`meta.Role` / API role DTOs replace `PlatformManage bool` with:

```go
ManageDatasources bool `json:"manageDatasources"`
ManageTables      bool `json:"manageTables"`
ViewAudit         bool `json:"viewAudit"`
ViewOutbox        bool `json:"viewOutbox"`
```

`meta.User` (session/request context) carries the same four flags from
the login/join query. All SQL touching `platform_manage` (roles CRUD,
`ListRoles`, user lookup) switches to the four columns.

### 3.3 Gates

`RequirePlatform` is replaced by four middleware constructors, each
passing on `IsAdmin || <flag>` and returning 403 `FORBIDDEN` otherwise:

| Gate | Protects |
|---|---|
| `RequireDSManage` | `/api/datasources*` (list, create, update, delete, test, introspect, columns) |
| `RequireTablesManage` | `/api/tables` create/update/delete, verify, resync, `/api/groups*`, `PATCH /api/tables/{id}` (set-group) |
| `RequireTablesManage` + `RequireDSManage` | `/api/meta/export`, `/api/meta/import/*` |
| `RequireAuditView` | `/api/audit` |
| `RequireOutboxView` | `/api/hooks/outbox*` (list + retry — the monitor) |

`GET /api/hooks` (list of hook names compiled into the binary) is gated by
`RequireTablesManage` instead: it feeds the hooks dropdown in the
definition editor, and a tables-manager without outbox access must still
be able to assign hooks.

### 3.4 Roles editor UI

`web/src/pages/Roles.tsx`: the single "Platform Management" switch becomes
four checkboxes with business-friendly labels + descriptions (i18n
`roles.grant.*`); the role list shows granted areas as short badges. The
Admin role keeps its all-powerful badge (immutable, not editable).

Table/row read visibility (`internal/api/tables.go` list + rows paths):
`!u.PlatformManage && !p.Read` becomes `!u.ManageTables && !p.Read`.

`GET /api/auth/me` returns `isAdmin, manageDatasources, manageTables,
viewAudit, viewOutbox` (drop `platformManage`).

## 4. Description & label polish

- `TableDef.Description string` (`json:"description"`), optional, capped
  at 200 chars, trimmed. Create/PUT accept it; empty string clears it.
- Metadata export includes `description`; import applies it (both for new
  and overwritten definitions).
- Sidebar (`web/src/components/Sidebar.tsx`): tooltip becomes the
  description when set (fallback: `schema.table`); label text unchanged.
- Data page: description renders as a muted, single-line-truncated
  subtitle under the table label heading; absent description renders
  nothing.
- TableForm wizard: the Label input moves to the top of its step with
  helper text ("This name appears in the menu for users") and a live
  preview line styled like a sidebar entry; a new optional Description
  textarea sits directly under it.

## 5. Humanized errors (frontend-only)

New helper `humanError(e: unknown): { title: string; detail?: string }`
in `web/src/lib/errors.ts` (i18n-aware):

- Map by `ApiError.code`: `HOOK_REJECTED`, `HOOK_MISSING`, `DRIFT`,
  `CONFLICT`, `CONN`, `FILTER_INVALID`, `IMPORT_BAD_CSV`,
  `META_FILE_INVALID`, `META_IMPORT_INVALID`, `RATE_LIMITED`,
  `GROUP_NAME_TAKEN`, `FILTER_NAME_TAKEN`, `EXPORT_TOO_LARGE`,
  `BULK_TOO_LARGE`, `VALIDATION`, `AUTH`, `FORBIDDEN`, `NOT_FOUND`,
  `INTERNAL`. Messages interpolate `message`/`detail` where useful
  (e.g. HOOK_REJECTED appends the hook's own rejection text).
- Unknown codes → title = raw `message`.
- `detail` (code, SQL state, validation specifics) renders behind a
  collapsed "View technical detail" disclosure wherever errors are shown.

Applied at the main user-facing failure points on the Data page (row
save/delete, bulk delete, filter save/load, drift banner, import preview
failures) and the login page rate-limit message. Form-level per-column
validation messages are already field-specific and unchanged.

## 6. i18n

New keys in both `en.ts` and `id.ts` (parity required, `npm run build`
does not enforce it — tests or a grep check in the plan do):

- `roles.grant.datasources` / `.tables` / `.audit` / `.outbox` (+ short
  business-friendly descriptions)
- `tables.description`, `tables.labelHint`, `tables.labelPreview`
- `errors.<CODE>` (~20 keys) + `errors.technicalDetail`
