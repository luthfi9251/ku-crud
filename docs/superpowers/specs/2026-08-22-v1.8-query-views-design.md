# Ku-CRUD v1.8 — Custom Query Views (Design Spec)

Date: 2026-08-22
Status: Implemented (see docs/superpowers/plans/2026-08-22-query-views.md)
Baseline: development @ v1.7

## 1. Goal

Let table managers define a table definition whose data source is not a
physical table but a user-written SQL SELECT. The query result becomes a
read-only grid with the same capabilities as a table-backed grid: server-side
search, sort, per-column filters, pagination, saved filters, CSV export,
sidebar grouping, drift detection and per-table read grants.

Deliverables:

1. `table_defs` gains `source_type` (`'table'` | `'query'`) and `query_sql`.
2. Query execution wraps the user query as a derived table
   (`SELECT cols FROM (query) AS ku_q ...`) so the entire existing
   list/count/filter pipeline is reused unchanged.
3. Layered execution guards: single-SELECT validation via `EXPLAIN` on the
   target server, read-only transaction, statement timeout, row cap.
4. Column introspection from the query (wizard parity with the existing
   3-step table wizard), with non-allowlisted result columns dropped and
   reported.
5. All write paths hard-blocked for query views (403 `QUERY_READONLY`).

Out of scope (YAGNI, deliberately not built): parameterized queries
(`$1`/`?` binding), result caching or materialization, SQL editor
autocomplete, a dedicated query-view RBAC grant, CREATE VIEW in the target
database (violates "Ku-CRUD never runs DDL").

## 2. Owner decisions (confirmed)

| Question | Decision |
|---|---|
| Who may create query views | **`manageTables`** — same trust class as table definitions (they already define defs over any table). Admin passes implicitly as today. |
| Grid depth over query results | **Full server-side** search/sort/filter/pagination via derived-table wrapping; saved filters and CSV export included. |
| Execution safety | **Layered guards** (4 layers, §5) rather than text validation alone. |
| Storage of `query_sql` | Column on `table_defs` (metadata DB), exported/imported by meta transfer like other definition attributes. |
| Key columns for query views | Optional; when absent the row-detail endpoint is disabled for that view. |

## 3. Data model (migration 11)

```sql
ALTER TABLE table_defs ADD COLUMN source_type TEXT NOT NULL DEFAULT 'table';
ALTER TABLE table_defs ADD COLUMN query_sql TEXT NOT NULL DEFAULT '';
```

- `source_type='table'` (default): behavior identical to today;
  `query_sql` stays empty.
- `source_type='query'`: `schema_name` and `table_name` are stored empty;
  `datasource_id` is still required (the query runs against that
  datasource). Columns are stored exactly like a table def (labels,
  searchable/sortable/visible flags, formatting, computed columns allowed).
- `key_columns` optional for query views — used only by the UI to identify
  rows; without it `GET /api/tables/{id}/rows/{pk}` returns 400 for that
  def.
- Backfill: none needed (default covers every existing row).

## 4. Definition validation (`validateDef` branch)

For `source_type='query'`:

- `query_sql` required, ≤ 20 000 chars, must start with `SELECT` or `WITH`
  (case-insensitive, after trimming whitespace/comments is NOT attempted —
  the fast prefix check is UX only; the authoritative check is EXPLAIN).
- `datasource_id` required; `schema_name`/`table_name` skipped.
- Key columns: each must be one of the defined columns (as today), but the
  "at least one key column" requirement is lifted.
- Column field types: `fk`, `m2m` rejected (`QUERY_READONLY` surface does
  not need them); `validations` and `hooks` rejected (write-path features);
  computed columns allowed (in-memory evaluation, unchanged).
- `default_sort_col`, view config (kanban/calendar), formatting: same rules
  as table defs.
- On save and on resync, the query must pass EXPLAIN validation (§5.1)
  against its datasource; failures return 400 `QUERY_INVALID` with the
  server error text.

## 5. Layered execution guards

Layer 1 — single-SELECT validation via EXPLAIN (authoritative).
On the target server run `EXPLAIN <query>` (Postgres) /
`EXPLAIN <query>` (MySQL). Planning rejects multi-statement input, DML/DDL
fragments and syntax errors; the drivers already refuse multi-statement in
one `Query()` as a free first line. String literals containing `;` remain
valid (still one statement). Users cannot smuggle `$1`/`?` placeholders —
EXPLAIN fails on unbound parameters, which is a natural guard.

Layer 2 — read-only transaction.
Postgres: `BeginTx(ctx, &sql.TxOptions{ReadOnly: true})`; the query and its
wrapper run inside. MySQL: check out a dedicated `*sql.Conn`, `SET SESSION
TRANSACTION READ ONLY`, run, then `SET SESSION TRANSACTION READ WRITE`
before returning the conn (drivers expose no per-query read-only).

Layer 3 — statement timeout (15 s).
Postgres: `SET LOCAL statement_timeout = '15s'` inside the read-only tx
(auto-resets at tx end). MySQL: `SET SESSION MAX_EXECUTION_TIME = 15000`
(applies to SELECT only — exactly our case) on the dedicated conn, reset to
`0` alongside the READ WRITE restore before the conn is returned. Bound
`pg_sleep`, seq scans on giant tables and accidental Cartesian products.

Layer 4 — row cap.
The wrapper always applies an outer `LIMIT`: `page_size` for grid pages
(1..200 as today) and `exportRowCap` (100 000, checked via COUNT first)
for CSV export — identical to the table path.

Layer 5 (unchanged, free): identifier allowlist — sort/search/filter
columns resolve only from stored metadata and re-quote via `QuoteIdent`;
values are bind parameters. The wrapped user query text is the only
non-parameterized fragment, and it is admin/table-manager authored, EXPLAIN
validated, read-only and time-boxed.

Failure mapping: EXPLAIN/validation → 400 `QUERY_INVALID`; timeout → 502
`QUERY_TIMEOUT`; row cap exceeded on export → 400 `EXPORT_TOO_LARGE`
(existing code).

## 6. Execution layer (`internal/ds`)

### 6.1 Wrapper builder (`sqlkit.go`)

New dialect-aware builder alongside the existing ones:

```
SELECT <cols> FROM (<query_sql>) AS ku_q
[WHERE <searchWhere + filterParts with baseRef="ku_q">]
ORDER BY <sortcol> <dir> LIMIT <ph> OFFSET <ph>
```

- `baseRef` is the quoted alias `ku_q` whenever filters exist (same
  ambiguity logic as fk joins today).
- Sort column must be in the selectable column list; direction whitelisted
  ASC/DESC — same rules as `buildList`.
- `buildQueryCount` mirrors it with `SELECT COUNT(*) FROM (...) AS ku_q
[WHERE ...]`.
- The user query text is interpolated verbatim inside the parens — it is
  definition data, not request data; request-controlled input never enters
  SQL text (unchanged posture).

### 6.2 Adapter additions (`Adapter` interface)

```go
ExplainQuery(query string) error          // layer 1; runs EXPLAIN
IntrospectQuery(query string) ([]LiveColumn, error)
ListQueryRows(p QueryParams) ([]map[string]any, error)
CountQueryRows(p QueryParams) (int, error)
```

- `IntrospectQuery` executes the wrapped query with `LIMIT 0` inside the
  read-only tx and reads `rows.ColumnTypes()`; maps database type names via
  the existing `MapFieldType`/`mapMySQLType`. Result columns that fail the
  identifier allowlist (e.g. unaliased expressions `?column?`, `count(*)`)
  are dropped and reported by name so the wizard can tell the user to add
  an alias.
- PG and MySQL implementations live in `postgres.go`/`mysql.go`, sharing a
  small `queryExec` helper that owns the read-only conn/tx + timeout
  lifecycle (layers 2–3).

### 6.3 `QueryParams`

```go
type QueryParams struct {
    Query      string
    Columns    []string        // stored, allowlisted
    Searchable []string
    Search     string
    SortCol    string
    SortDir    string
    Filters    []ColumnFilter  // fk joins excluded by validation
    Limit      int
    Offset     int
}
```

## 7. API surface

All existing endpoints keep their paths; query views are table defs.

| Endpoint | Behavior for `source_type='query'` |
|---|---|
| `POST/PUT /api/tables` | Accepts `sourceType`, `querySql`; query branch of validation; EXPLAIN on save. |
| `GET /api/tables`, `GET /api/tables/{id}` | Unchanged; DTO carries `sourceType`, `querySql` (visible to anyone who can already see the def — same disclosure level as `schemaName`/`tableName` today). |
| `GET /api/tables/{id}/rows` | Query execution path (§6); `read` grant enforced as today. |
| `GET /api/tables/{id}/rows/export` | Query path with export cap; `read` grant. |
| `GET/POST/PUT/DELETE .../saved-filters` | Unchanged (validated against stored columns). |
| `GET /api/tables/{id}/verify` | Runs EXPLAIN + `IntrospectQuery`, then existing `CompareDrift` against stored columns — drift detection works for queries too. |
| `POST /api/tables/{id}/resync` | Replaces stored columns from introspection (same flow as table resync). |
| `GET .../rows/{pk}` | 400 `QUERY_NO_KEY` when the def has no key columns; otherwise query path. |
| `POST/PUT/DELETE .../rows`, `bulk-delete`, `import/*`, `fkoptions/*`, `m2m*` | 403 `QUERY_READONLY` early guard. |
| `POST /api/datasources/{id}/query-introspect` (**new**) | `RequireDSManage`. Body `{query}`. Runs EXPLAIN + introspection; returns `{columns, dropped}`. Powers the wizard's step 2. |

Write-path guard placement: single helper `if def.SourceType == "query" {
writeErr(403, "QUERY_READONLY", ...) }` at the top of each write handler —
mirrors the existing per-table grant checks.

## 8. RBAC

- Definition create/update/delete: `RequireTablesManage` (unchanged gate);
  Admin implicit.
- Row read + export: `role_table_grants.can_read` per def, unchanged;
  create/update/delete grants are ignored (backend 403s regardless, UI
  hides write actions).
- Sidebar grouping, table-list visibility (`manageTables` sees all defs),
  token-ID masking: unchanged.
- `POST /api/datasources/{id}/query-introspect` requires
  `manageDatasources` (it opens a live datasource connection, like the
  existing introspect endpoint it sits beside).

## 9. Meta transfer

`metaFileTable` += `sourceType`, `querySql`. Export includes them
(query text is not a credential; password-free export stays true).
Import: `validateBundleTable` runs the query-view branch; on apply, EXPLAIN
validation runs against the selected local datasource — a query view whose
datasource is not selected/imported is rejected with the existing
dependency-error style message.

## 10. Frontend (summary)

- Wizard step 1 gains a source toggle: *Physical table* | *SQL query*.
- Query mode step 2: SQL textarea (monospace, no autocomplete), live
  "Validate & preview columns" button calling `query-introspect`, dropped
  columns listed with a hint to alias them.
- Data page: read-only view — create/edit/delete/import/bulk actions
  hidden; search/sort/filter/pagination/export/saved filters active.
- Definition editor hides fk/m2m/hooks/validations sections for query
  defs; computed columns and formatting stay.
- i18n: new keys (`QUERY_INVALID`, `QUERY_READONLY`, `QUERY_NO_KEY`,
  `QUERY_TIMEOUT`) mapped to friendly ID/EN sentences per the v1.7
  humanization pattern.

## 11. Testing

1. `sqlkit_test.go`: wrapper builder both dialects — placeholder
   numbering with filters+pagination, sort/search/filter payloads stay bind
   args (SQL-injection posture probes, extending the existing hostile-input
   tests).
2. Live PG/MySQL tests (pattern of `filters_pg_test.go`):
   - EXPLAIN rejects `SELECT 1; DROP TABLE x`, `UPDATE ...`, unaliased
     parameter `$1`, garbage syntax.
   - Read-only tx rejects a query with side-effect functions (e.g.
     `SELECT setval(...)` fails).
   - Timeout fires on `SELECT pg_sleep(30)` (PG) using a lowered test
     timeout.
   - Introspection returns typed columns; unaliased expression columns are
     dropped and reported.
3. API tests (`api` package, httptest):
   - Table manager creates query def; plain user with `can_read` lists and
     exports rows; no-grant user 403.
   - Every write endpoint returns 403 `QUERY_READONLY` for query defs.
   - Verify/resync drift flow on a changed query.
   - Meta export→import round-trip carries `sourceType`/`querySql`.
4. Regression: existing table-def flows untouched (default `source_type`
   branch = old code path).

## 12. Rollout

Single migration (11), default-safe. Backend and frontend ship together in
one release (project convention). No feature flag — the new source type is
inert until a manager creates a query view.
