# Ku-CRUD v1.6 — Automation via Go Hooks (Design Spec)

Date: 2026-08-22
Status: Approved (decisions confirmed with owner)
Baseline: development @ e30365f (v1.5 + docs page merged)

## 1. Goal

Give developers the freedom to run custom logic without building a new
service. A developer writes a plain Go function in `hooks/`, the build
registers it, and the table definition assigns it to a CRUD event.
Production deployment still requires a binary rebuild — hooks are trusted,
compiled, type-safe Go code that can be unit tested.

Deliverables:

1. Hook mechanism: 6 events (before/after × create/update/delete),
   explicit registry populated by a build-time code generator.
2. Hook assignment per table definition (event → ordered hooks + JSON config).
3. After-hooks run on an async worker backed by a durable SQLite outbox
   with automatic retry (backoff) and manual retry from an admin page.
4. Missing-hook policy: a definition referencing a hook absent from the
   binary rejects writes with a clear error — drift never happens silently.
5. Hook context: lazy access to every registered datasource adapter, the
   metadata store, and a logger — the "no new service" promise.
6. Trigger consistency: hooks fire from a shared executor called by every
   write path (form, CSV import, bulk delete, kanban drag, m2m link sync).
   Import preview runs before-hooks so hook-rejected rows surface before
   insert.

Out of scope: hot-loading hooks at runtime (Go plugins / interpreters),
hook versioning, per-user hooks, a hook marketplace/management UI beyond
the outbox monitor, purging/archiving outbox entries.

## 2. Owner decisions (confirmed)

| Question | Decision |
|---|---|
| Registry population | **Build-time codegen** — `go:generate` AST scanner writes `hooks/registry_gen.go` (name → func). No manual registration, no runtime watcher. A new hook appears after rebuild + restart (dev loop already restarts). |
| Hook catalog storage | **In-memory registry only** (served via `GET /api/hooks`). No SQLite catalog table — the registry is the source of truth, a DB copy would go stale. SQLite stores only assignments and the outbox. |
| Integration architecture | **Shared hook executor** (`RunBefore` / `EnqueueAfter` helpers) called from the 4 existing write paths. No full service-layer extraction — consistency is enforced by convention + tests, mirroring the existing `auditBestEffort` helper pattern. |
| m2m junction writes | **Junction hooks fire** — m2m link insert/delete is a write to the junction definition; its hooks run like any other write. No write path silently bypasses hooks. |
| Retry policy | **5 attempts**, backoff 30s → 2m → 10m → 1h → 4h, then `dead` (manual retry only). Before-hook timeout **5s** (synchronous, blocks the request); after-hook timeout **30s** (async worker). |
| Before-hook value mutation | Modified values are used **without re-validation** (hook code is trusted; raw input was already validated by `editablePayload`). Unknown column names in the modified payload are still rejected. |
| Failed outbox enqueue | **Best-effort with WARN log** (same policy as audit writes) — the data write is already committed; rollback is impossible and not attempted. |

## 3. Architecture

```
hooks/*.go                 plain Go functions (developer-owned, no registration)
hooks/gen.go               //go:generate entry
hooks/registry_gen.go      generated map: hook name → HookFunc
        │ generated by
cmd/hookgen/               AST scanner (go/ast): finds funcs matching the
                           HookFunc signature in hooks/*.go, writes
                           registry_gen.go; skips non-matching funcs silently
        │
cmd/main.go                api.New(store, registry) + starts outbox worker
        │
internal/hooks/            contract + runtime:
  - Event, HookFunc, HookContext, RowPayload, Registry, HookInfo
  - Executor: RunBefore (sync, timeout 5s, recover), buildAfter (enqueue)
internal/meta/             migration 9: table_defs.hooks + hook_outbox;
                           outbox store CRUD
internal/api/              GET /api/hooks, outbox endpoints, write paths
                           call the executor
web/                       TableForm hooks section, /hooks-outbox monitor page
```

Dependency direction: `hooks → internal/hooks → (ds, meta)`. `internal/api`
depends only on `internal/hooks` types (the registry is injected into
`api.New` behind a minimal interface so `internal/api` never imports the
developer's `hooks` package).

## 4. Hook contract

```go
package hooks // internal/hooks

type Event string

const (
    BeforeCreate  Event = "beforeCreate"
    AfterCreate   Event = "afterCreate"
    BeforeUpdate  Event = "beforeUpdate"
    AfterUpdate   Event = "afterUpdate"
    BeforeDelete  Event = "beforeDelete"
    AfterDelete   Event = "afterDelete"
)

type HookFunc func(ctx context.Context, hc *HookContext, ev Event,
    row RowPayload, cfg json.RawMessage) (RowPayload, error)

type HookContext struct {
    User      ActingUser         // id, username of the acting user
    TableDef  *meta.TableDef     // definition holding the assignment
    Columns   []meta.ColumnDef
    Open      func(datasourceID int64) (ds.Adapter, error) // lazy; hook must Close
    Store     *meta.Store        // read definitions / audit
    Logger    *slog.Logger
}

type RowPayload struct {
    Values map[string]any // new values (create/update); mutable by before-hooks.
                           // Empty map for delete events.
    Old    map[string]any // previous row (update/delete); nil on create.
}
```

Semantics:

- **Before-hook**: runs synchronously before the DB query. May modify
  `Values` (trusted; no re-validation — but the write path still rejects
  unknown column names via `editablePayload` on the modified payload).
  Returning an error rejects the operation: HTTP 400 `HOOK_REJECTED`,
  message forwarded verbatim; the query never runs.
- **After-hook**: side effects only; return value ignored beyond success.
  Executed exclusively by the async worker from the outbox, never inside
  the request.
- Every execution is wrapped in `context.WithTimeout` (5s before / 30s
  after) and `recover()` — a panicking or hung hook becomes an error, never
  a crash.
- Hook name = Go function name. Renaming a function creates a new hook;
  assignments referencing the old name hit the missing-hook policy.

## 5. Code generator (cmd/hookgen)

- `hooks/gen.go` carries `//go:generate go run ../cmd/hookgen`.
- The generator parses every `hooks/*.go` except `registry_gen.go` with
  `go/parser`, selects top-level funcs whose signature matches
  `func(context.Context, *hooks.HookContext, hooks.Event, hooks.RowPayload, json.RawMessage) (hooks.RowPayload, error)`
  and writes `hooks/registry_gen.go`:

  ```go
  // Code generated by cmd/hookgen. DO NOT EDIT.
  package hooks

  func init() {
      internal/hooks.Register("normalize_price", normalize_price)
      ...
  }
  ```

  Wiring: `internal/hooks` exposes `Register(name, fn)`. The developer's
  `hooks` package already imports `internal/hooks` for the signature types,
  so `registry_gen.go` (package `hooks`) calling `internal/hooks.Register`
  adds no new dependency edge: `hooks → internal/hooks → (ds, meta)`. No
  cycle exists.
- `make dev` and `make build` run `go generate ./hooks` before compiling;
  `go build ./cmd` alone embeds the last generated registry (documented).
- One example hook ships in `hooks/example.go` as living documentation
  (e.g. a before-create normalizer and a no-op after-create logger).

## 6. Assignment on the table definition (migration 9)

`table_defs` gains `hooks TEXT NOT NULL DEFAULT ''` — a JSON object keyed
by event, following the v1.5 `view_config` pattern:

```json
{
  "beforeCreate": [{"hook": "normalize_price", "config": {"round": 2}, "order": 1}],
  "afterCreate":  [{"hook": "sync_inventory", "config": {}, "order": 1}]
}
```

- Assignment list is ordered by `order` (stable: equal orders run in list
  order); `config` is an arbitrary JSON object passed verbatim to the hook.
- **Save-time validation** (`handleTableCreate/Update`): hook names checked
  against the registry; unknown name → 400 naming the hook. Fast UX, but
  the real guarantee is the runtime check (a binary can be older than the
  metadata).
- `GET /api/hooks` (`RequirePlatform`) returns `[{name}]` for the
  TableForm dropdown.
- Meta export/import (v1.4) carries `hooks` as names. Import **succeeds**
  even when a hook is absent from the target binary; the missing-hook
  policy applies on write. Drift is explicit, never silent.

## 7. Execution flow

### 7.1 Runtime guards (every write path)

Before any operation, the write path resolves the definition's hook
assignments and verifies every referenced name exists in the registry.
Missing → HTTP 400 `HOOK_MISSING` naming the hook. The check runs once per
request (not per row) — for import/bulk the whole request is rejected up
front.

### 7.2 Before-hooks (sync, in-request)

Order of operations per write path:

1. Existing validation (`editablePayload`, m2m strip/precheck) — unchanged.
2. `HOOK_MISSING` guard.
3. Before-hooks in `order`, each with 5s timeout + recover. Modified
   `Values` become the payload; the modified payload re-enters
   `editablePayload` filtering (unknown column names rejected; values not
   re-validated).
4. Existing FK checks → Insert/Update/Delete → m2m sync → audit.

Call sites: rows create/update/delete, import apply (per row), bulk delete
(per key), m2m link sync (junction definition's beforeCreate/beforeDelete
for link insert/remove), kanban drag (goes through rows update —
automatic).

### 7.3 After-hooks (async, durable outbox)

After commit + audit, the write path enqueues one outbox entry **per
assignment** (an update with two after-update hooks → two entries, retried
independently). Entries snapshot the row (old/new values). Import/bulk
enqueue after the whole batch completes — still one entry per row per
assignment.

Outbox insert failure → WARN log (best-effort, `auditBestEffort` policy).

### 7.4 Import preview

`validateImportRows` runs before-hooks per row in validation-only mode
(no commit): a hook error marks the row invalid with the hook's message.
The executor supports invocation without a live write.

## 8. Outbox store & worker (migration 9)

```sql
CREATE TABLE hook_outbox(
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  table_def_id INTEGER NOT NULL REFERENCES table_defs(id) ON DELETE CASCADE,
  event        TEXT NOT NULL,
  hook_name    TEXT NOT NULL,
  config       TEXT,
  old_values   TEXT,
  new_values   TEXT,
  user_id      INTEGER NOT NULL DEFAULT 0,
  username     TEXT NOT NULL DEFAULT '',
  status       TEXT NOT NULL DEFAULT 'pending',   -- pending | done | dead
  attempts     INTEGER NOT NULL DEFAULT 0,
  next_retry_at TEXT,
  last_error   TEXT,
  created_at   TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at   TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_hook_outbox_due ON hook_outbox(status, next_retry_at);
```

`user_id`/`username` snapshot the acting user so after-hooks (executed
later, after the session is gone) still know who triggered the write —
the same reason the audit table records the user.

- Worker: goroutine started in `cmd/main.go` after `api.New`, graceful
  stop via context. Polls every 5s for `status='pending' AND
  (next_retry_at IS NULL OR next_retry_at <= now)` entries, claims the 10
  oldest, executes each after-hook (30s timeout, recover).
- Success → `done`. Failure → `attempts++`; if `attempts >= 6` → `dead`,
  else `next_retry_at` = backoff[`attempts`] after the failed execution:
  1 → 30s, 2 → 2m, 3 → 10m, 4 → 1h, 5 → 4h. One initial execution + five
  retries = six total executions, matching the owner decision "retry 5x,
  backoff up to 4h, then dead".
- Manual retry: `POST /api/hooks/outbox/{id}/retry` resets attempts and
  sets status `pending` (allowed from `dead` or a scheduled retry).
- `meta.Store` is single-connection (`SetMaxOpenConns(1)`); worker queries
  serialize with API traffic — acceptable, metadata operations are small.
- One worker per process; no leader election needed (single-binary
  deployment model).

## 9. API additions

| Method | Endpoint | Gate | Description |
|---|---|---|---|
| GET | `/api/hooks` | Platform | Registered hook names (dropdown source) |
| GET | `/api/hooks/outbox?status=&tableDefId=&page=` | Platform | Outbox monitor with filters |
| POST | `/api/hooks/outbox/{id}/retry` | Platform | Manual retry |

New error codes: `HOOK_REJECTED` (400, before-hook refused the write),
`HOOK_MISSING` (400, assignment references a hook absent from the binary).

## 10. Frontend

- **TableForm.tsx**: "Hooks" section — per event (6), an ordered list of
  assignments (hook dropdown from `GET /api/hooks`, JSON config textarea,
  reorder). Shown only when the registry is non-empty, so instances
  without hooks see no dead UI.
- **Outbox page** (`/hooks-outbox`, sidebar under Audit, Platform-only):
  table of entries (created, table label, event, hook, status, attempts,
  last error), status filter, retry button on failed/dead entries. No
  purge action (YAGNI; outbox volume is low and SQLite is a single file).
- i18n ID/EN dictionaries, `types.ts`, Docs page and README updated
  (including the dev flow: add function → `make dev`/`make build` → hook
  appears; rename = new hook).

## 11. Testing

- **Unit (no DB, self-skipping pattern not needed)**: hookgen AST scanner
  (matching/non-matching signatures, name extraction), registry lookup,
  executor timeout + panic recovery + value mutation, outbox store CRUD
  and backoff computation (in-memory or temp SQLite file), worker claim
  loop with a fake registry.
- **Integration (PG/MySQL-gated, existing pattern)**: before-hook rejects
  and modifies writes; after-hook enqueued then executed; import preview
  marks hook-rejected rows invalid; `HOOK_MISSING` on write after
  simulated registry loss; m2m junction hooks fire on link changes;
  regression safety net = existing `rows_write_test.go`,
  `import_test.go`, `bulk_test.go`, `m2m_test.go`.

## 12. Risks

- **Write-path regression** is the biggest risk; mitigated by touching the
  four paths with minimal diffs and keeping every existing write test
  green.
- Generated-file drift if someone edits `registry_gen.go` by hand —
  header says DO NOT EDIT; regenerating is part of `make dev`/`make build`.
- `json.RawMessage` config blobs are free-form; a malformed config is
  surfaced to the hook (it decides whether to error), not validated at
  assignment save beyond JSON-parseability.
