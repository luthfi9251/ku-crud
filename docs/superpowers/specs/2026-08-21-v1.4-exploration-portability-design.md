# Ku-CRUD v1.4 — Advanced Exploration, Portability & Navigation (Design Spec)

Date: 2026-08-21
Status: Approved (decisions confirmed with owner)
Baseline: v1.3 (main @ e6d6567)

## 1. Goal

Find data with precision (per-column advanced filtering, applied everywhere
including CSV export), move definitions between environments (metadata
export/import as one JSON file), guarantee data quality (per-column validation
rules on every write path), and keep the sidebar navigable as the number of
table definitions grows (table grouping + a data-page shortcut to the
definition editor).

Out of scope (per brief): keyset/cursor pagination (removed from v1.4 brief by
owner), MongoDB adapter, M2M column filtering, saved filters (v1.5), grants or
roles inside the metadata export file.

## 2. Owner decisions (confirmed)

| Question | Decision |
|---|---|
| Sidebar grouping scope | Global (same structure for every user), managed only by Platform Management users. |
| FK column filtering | Filters match the **display value** of the target table via LEFT JOIN (not the raw ref id). |
| "Number only" validation | Digits with optional decimal point and leading minus: `^-?[0-9]+(\.[0-9]+)?$`. |
| Export file contents | Datasources (no passwords) + table definitions (with columns, relations, validations) + sidebar groups. No grants, no roles. |
| Datasource passwords on import | Prompted per new datasource inside the import wizard; apply refuses a new datasource without a password. |

Architecture approach: extend the existing patterns (Approach A) — filters as
a first-class field on the shared `ListParams`, validation rules as a JSON
column on `columns`, metadata export as a new natural-key JSON format, sidebar
groups as a new metadata table. No new abstraction layers.

## 3. Feature designs

### 3.1 Advanced Filtering

**Backend**

- New shared type in `internal/ds/adapter.go`:

  ```
  type ColumnFilter struct {
      Column string   // must exist in the table definition
      Op     string   // operator, see matrix below
      Values []string // string form; converted per column type at build time
  }
  ```

  `ListParams` gains `Filters []ColumnFilter`. `buildList` and `buildCount`
  (`internal/ds/sqlkit.go`) append filter predicates to the WHERE clause with
  bound parameters; identifiers go through `QuoteIdent` exactly like existing
  sort/search handling.

- Operator matrix (enforced per column field type):

  | Field type | Operators |
  |---|---|
  | text, uuid | `eq`, `neq`, `contains`, `in` |
  | number | `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `between`, `in` |
  | datetime | `eq`, `gt`, `lt`, `between` (both bounds inclusive, date or datetime strings) |
  | boolean | `eq` (`true`/`false`) |
  | enum | `eq`, `neq`, `in` |
  | fk | `contains`, `eq` — matched against the target table's **display columns** via LEFT JOIN |
  | m2m | not filterable in v1.4 |

- Value arity: `between` = exactly 2; `in` = 1..50; all others = exactly 1.
  Max 10 filters per request (AND combination). `contains` uses the existing
  dialect behavior (`ILIKE` on PG / `LIKE` on MySQL) with `escapeLike`;
  boolean `eq` parses `true|false`; number/datetime values are type-checked
  against the same layouts used by `validateValue` before the query runs.

- **FK join**: when at least one fk filter is present, `buildList`/`buildCount`
  add one `LEFT JOIN <target schema.table> f_<col> ON f_<col>.<refCol> =
  base.<fkCol>` per filtered fk column; the predicate applies `contains`/`eq`
  against the join's display columns (OR across multiple display columns,
  concatenated match not required). The join is added for the filter request
  only — the unfiltered path is byte-identical to today.

- **Validation & errors**: `handleRowList` (`internal/api/rows.go`) parses the
  `filters` query param (URL-encoded JSON array), resolves each column against
  the stored definition, checks operator-vs-type and value arity, and rejects
  with 400 `{code: "FILTER_INVALID", detail: {…per-filter message}}` on any
  violation. Column names and operators never reach SQL other than through the
  metadata allowlist — same anti-injection posture as sort/search today.

- **CSV export**: `handleRowExport` accepts and parses the same `filters`
  param through the same validation helper, so exports follow the active
  filters exactly (search/sort already do).

**Frontend** (`web/src/pages/Data.tsx`)

- Filter bar above the grid: "Add Filter" opens a popover — column select
  (visible, non-m2m columns only) → operator select (filtered by column type)
  → value input(s): text input, number input, date picker(s) for
  between/date-range, multi-chip input for `in`, true/false select for boolean,
  enum options select.
- Active filters render as removable chips; editing a filter resets page to 1.
  Filter state is per-table and resets on table change (search behaves the
  same way today).
- `exportCSV` appends the `filters` param to the download URL.

### 3.2 Export & Import Metadata Definition

**File format** (`format: "ku-crud-meta"`, `version: 1`) — natural keys only,
no internal ids, no masked tokens, no passwords:

```json
{
  "format": "ku-crud-meta",
  "version": 1,
  "exportedAt": "2026-08-21T10:00:00Z",
  "groups": [ { "name": "Sales" } ],
  "datasources": [
    { "name": "prod-pg", "adapter": "postgres", "host": "…", "port": 5432,
      "database": "…", "user": "…", "sslMode": "…" }
  ],
  "tables": [
    { "datasourceRef": "prod-pg", "schema": "public", "table": "customers",
      "label": "Customers", "keyColumns": ["id"], "pageSize": 50,
      "defaultSortCol": "id", "defaultSortDir": "ASC", "groupRef": "Sales",
      "columns": [
        { "name": "email", "fieldType": "text", "label": "Email",
          "editable": true, "required": true, "visible": true,
          "searchable": true, "sortable": true, "position": 1,
          "enumOptions": [], "validations": [ { "type": "email" } ],
          "fkTableRef": null, "fkRefColumn": "", "fkDisplayColumns": [],
          "m2mJunctionTableRef": null, "m2mJunctionSrcCol": "",
          "m2mJunctionTgtCol": "", "m2mDisplayColumns": [] }
      ] }
  ]
}
```

- FK references are serialized as `fkTableRef: {datasourceRef, schema, table}`
  (plus `junctionTableRef` for m2m) so relations survive the id remap.
- Export includes **all** datasources, all table defs, all groups — one file,
  no selection UI on export.

**Endpoints** (all Platform Management only)

| Method/Path | Purpose |
|---|---|
| `GET /api/meta/export` | download the JSON file above |
| `POST /api/meta/import/preview` | upload file; validate & diff; no writes |
| `POST /api/meta/import/apply` | execute selected imports in one SQLite transaction |

- **Preview**: parses the file, rejects unknown `format`/`version` or malformed
  structure (400 `META_FILE_INVALID` with the first structural error). Each
  item is matched against local metadata by natural key (datasource: name;
  table: datasource+schema+table; group: name) and reported as
  `new` / `duplicate-identical` / `duplicate-conflicts` (field-level diff
  summary for tables). The response also lists each table's dependency refs
  (fk/m2m targets) and flags any that resolve neither locally nor inside the
  file — such tables are marked `invalid-dependency` and cannot be selected
  for import until their target is selected too or already exists locally.
- **Apply** payload (table refs are `"<datasource>/<schema>/<table>"`):

  ```json
  { "datasources": [ { "ref": "prod-pg", "mode": "skip|overwrite", "password": "…" } ],
    "tables":     [ { "ref": "prod-pg/public/customers", "mode": "skip|overwrite" } ],
    "groups":     true }
  ```

  Behavior:
  - new datasource: create (password required — wizard prompts; empty → 400).
  - existing datasource + `overwrite`: update connection fields; **keep the
    existing password** (a provided password, if any, replaces it).
  - new table: create def + columns (id remapped from refs), run `validateDef`
    after remap; missing group refs are created.
  - existing table + `overwrite`: update def fields and replace the column set
    (existing `ReplaceColumns` path); grants untouched; row data untouched.
  - `duplicate-identical` + overwrite = no-op. Unselected items are skipped.
  - Everything runs in one SQLite transaction: any hard failure rolls the
    whole apply back (metadata is local and small — unlike CSV import,
    partial success is not needed here).
  - One audit entry (`action: "meta_import"`, detail: counts) on success.
  - Live-schema verification against the target database is deliberately **not**
    performed during import (the target env may not be reachable yet); the
    existing drift/resync flow covers it afterwards.

**Frontend** — new page under the Platform section: "Definitions Transfer"
(`#/meta`). Two cards: Export (button, downloads `ku-crud-meta-<date>.json`)
and Import wizard following the v1.3 CSV-import wizard pattern: upload →
item table with per-item status and skip/overwrite selects → password inputs
for each selected new datasource → apply → result summary.

### 3.3 Per-Column Validation Rules

- `ColumnDef` gains `Validations []ValidationRule` (JSON `validations`):

  ```
  type ValidationRule struct {
      Type  string // "email" | "min_len" | "max_len" | "number" | "text"
      Param int    // min_len / max_len bound; ignored otherwise
  }
  ```

- Rules available to any editable column (typically text); multiple rules per
  column combine (all must pass).
- Single enforcement point: `applyColumnValidations(col, value)` called from
  `validateValue` (`internal/api/validate.go`) after type coercion — which
  automatically covers create, update, **and CSV import** (which funnels
  through `coerceValidate` → `validateValue`). Rules evaluate the string form
  of the value; empty/null values are skipped (presence is the `required`
  flag's job).
  - `email`: `^[^@\s]+@[^@\s]+\.[^@\s]+$`
  - `min_len` / `max_len`: rune count of the string form, inclusive bounds
    (param 1..1000, validated at definition save).
  - `number`: `^-?[0-9]+(\.[0-9]+)?$` (digits, optional decimal, optional
    leading minus — owner decision).
  - `text`: letters and spaces only (`^[A-Za-zÀ-ÿ ]+$` incl. accented Latin).
- Failure → 400 with per-column messages `{errors: {<col>: ["…", …]}}` (same
  shape as today's field errors); CSV import preview marks the cell invalid
  with the rule's message.
- Definition-save validation (`validateDef`): rule types allowlisted, params
  in range, at most one rule of each type per column.
- Wizard UI (`ColumnListEditor`): per-column "Validations" row (visible when
  the column is editable): checkboxes for email / number / text, two number
  inputs for min/max length.

### 3.4 Sidebar Table Grouping

- New metadata: `table_groups(id, name UNIQUE NOT NULL, position INTEGER)`;
  `table_defs.group_id INTEGER NULL REFERENCES table_groups(id) ON DELETE SET
  NULL`. Deleting a group returns its tables to the ungrouped list — tables
  are never deleted by group operations.
- API: `GET /api/groups` is readable by **all authenticated users** (the
  sidebar needs group names to render for everyone); mutations are PM only —
  `POST /api/groups`, `PATCH/DELETE /api/groups/{id}` (rename, reposition via
  `position`; position is a dense ordering int, up/down moves implemented as
  position swaps). Moving a table between groups uses the existing
  `PATCH /api/tables/{id}` with a nullable `groupId`.
- Sidebar (`web/src`): groups render as collapsible sections ordered by
  `position`, then ungrouped tables exactly as today. All users see the same
  structure; only PM users get the "manage groups" affordance: inline
  create/rename/delete, up/down reorder, and a per-table "Move to group"
  menu. No drag-and-drop in v1.4 (buttons/menus only — smaller surface,
  keyboard accessible).
- Group name constraints: 1..60 chars, unique; audit entries for group
  create/update/delete (platform action).

### 3.5 Data-Page Shortcut to Table Definition

- Pure frontend: an icon button ("Definition") in the `Data.tsx` toolbar,
  rendered only when the current user has Platform Management access.
  Navigates to `/tables` with router state `{openDef: <tableDefId>}`; the
  Tables page opens the definition editor for that def on mount. No backend
  changes.

## 4. Data model changes (migration 7)

```sql
CREATE TABLE table_groups (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  name     TEXT NOT NULL UNIQUE,
  position INTEGER NOT NULL DEFAULT 0
);
ALTER TABLE table_defs ADD COLUMN group_id INTEGER REFERENCES table_groups(id) ON DELETE SET NULL;
ALTER TABLE columns ADD COLUMN validations TEXT NOT NULL DEFAULT '';
```

## 5. API surface summary (new)

| Method/Path | Gate | Purpose |
|---|---|---|
| `GET /api/meta/export` | PM | metadata JSON download |
| `POST /api/meta/import/preview` | PM | validate + diff uploaded file |
| `POST /api/meta/import/apply` | PM | apply selections transactionally |
| `GET /api/groups` | auth (read) | group list for sidebar rendering |
| `POST /api/groups` | PM | create group |
| `PATCH/DELETE /api/groups/{id}` | PM | rename/reposition / delete |

Changed: `GET /api/tables/{id}/rows` and `GET /api/tables/{id}/rows/export`
accept `filters`; `PATCH /api/tables/{id}` accepts `groupId`; table def
payloads expose `validations` per column and `groupId`/`groupName` per def;
the sidebar fetches `GET /api/groups` alongside its existing table list.

## 6. Error handling

- Filter violations: 400 `FILTER_INVALID` with per-filter detail; unknown
  column, wrong operator for type, wrong arity, unparseable value each named.
- Metadata import: 400 `META_FILE_INVALID` (structure/version), 400
  `META_IMPORT_INVALID` (missing password for new datasource, dependency
  target absent, `validateDef` failure after remap — item named), whole-apply
  rollback on hard failure.
- Validation rules: 400 with `{errors: {col: [messages]}}` on create/update;
  per-cell invalid marks in CSV import preview.
- Groups: 409 `GROUP_NAME_TAKEN` on duplicate name; delete always succeeds
  (tables fall back to ungrouped).

## 7. Testing

Backend (Go):
- unit: filter parsing/validation matrix (bad column, bad op-for-type, arity,
  value coercion, injection payloads in column/op/value), per-dialect WHERE
  building incl. fk LEFT JOIN SQL text, `applyColumnValidations` matrix
  (valid/invalid/boundary per rule, combined rules, empty values), metadata
  serializer (def → file JSON, no password/id leakage), importer round-trip
  (new/identical/conflicts, fk+m2m remap, group auto-create, missing
  dependency, transactional rollback, password kept on overwrite), groups
  CRUD + position swap + delete → tables ungrouped.
- integration (PG): filtered list/count/export agree on totals; fk display
  filter via join; filter + search + sort combined; validation rule rejects
  insert/update and CSV import row.
- MySQL-gated: filter SQL smoke (backtick quoting, `LIKE` case behavior),
  import/export metadata smoke.

Frontend: `npm run build` (strict tsc) + `oxlint` (repo convention; no FE test
framework). Verification commands per README: `go vet ./...`, `gofmt -l .`,
`go test ./...` plus `KUCRUD_TEST_PG`/`KUCRUD_TEST_MYSQL` variants.

## 9. Risks / trade-offs accepted

- `filters` as a JSON query param caps at 10 filters — URL length stays
  bounded; saved filters (v1.5) will move composition client-side anyway.
- FK display filters add a LEFT JOIN per filtered fk column — bounded by the
  10-filter cap; users filtering huge unindexed target tables own that cost
  (same as global search today).
- M2M columns are not filterable in v1.4 (junction aggregation is a separate
  query shape) — surfaced as disabled in the filter UI, revisited with v1.5.
- Import does not verify the live schema of the target environment — drift
  detection is the existing answer; documented in the wizard result card.
- Validation rules run on the string form of values (not the driver-typed
  form) — deterministic across adapters; edge rules on non-text types are
  best-effort and documented.
- Group reorder is position-swap based (no arbitrary drag ordering) — simpler,
  race-safe with two writers at this scale.
